# MCP（Model Context Protocol）协议研究报告

## 摘要

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月 25 日发布并开源的开放通信标准，基于 JSON-RPC 2.0，用统一的 Host/Client/Server 架构规范大模型与外部数据源、工具之间的连接方式 [4][6][7][10]。它要解决的核心痛点是 N×M 集成难题——N 个 AI 应用对接 M 个工具时需维护 N×M 个定制连接器，同时缓解工具接入碎片化、供应商锁定与上下文割裂问题，把 N×M 降为 N+M [10][11][13][15][18]。截至 2026 年，MCP 已发布至 2026-07-28 第 5 版规范（v2），完成向 Linux Foundation 旗下 Agentic AI Foundation 的治理捐赠，四大 Tier 1 SDK 月下载量达 4 亿量级，主流 IDE、Agent 框架与云厂商广泛支持 [11][21][22][25]。但生态仍处早期：公开服务器数量各口径差异巨大（官方商店 950+ 至第三方目录 17,520+），企业落地面临权限模糊、提示注入、供应链投毒与"影子 IT"等突出安全治理问题 [21][23][24][29][30]。总体判断：MCP 已成为 Agent 连接外部世界的事实标准接口，但"连接标准已定、安全与治理标准未定"是当前生态的基本特征。

## 一、MCP 是什么：技术定义与核心架构

### 1.1 定义与协议基础

MCP 是一种开放标准，旨在统一大模型与外部数据源、工具和应用之间的通信，打破数据孤岛、提升互操作性 [4][5][6]。其协议层基于 JSON-RPC 2.0，采用纯 JSON 封装三类消息：带唯一 ID 的请求、含结果或错误的响应、以及无需回复的通知；请求响应匹配、错误传递和并发管理由协议层自动处理 [1][2]。相比 gRPC 等二进制协议，JSON 消息可人工阅读、更易调试 [1]。

### 1.2 三层角色架构

- **Host（主机应用）**：启动连接的 LLM 应用，如 Cursor、Claude Desktop、Cline、AI IDE 或 AI Agent，是用户交互点，负责任务执行与交互 [1][4][5]。
- **Client（客户端）**：位于 Host 内部，与 Server 保持 1:1 连接；一个 Host 可运行多个 Client 同时连接多个 Server。Client 负责协议通信、初始化时协商功能与协议版本、管理工具调用请求与响应、处理服务器通知 [1][2][4]。
- **Server（服务器）**：独立运行的轻量程序，可本地或远程部署，负责功能注册（暴露原语）、请求处理、上下文提供、状态管理与实时通知 [1][2][5]。

### 1.3 服务器三类核心原语

| 原语 | 定位 | 典型示例 | 关键约束 |
|---|---|---|---|
| **Tools（工具）** | 可被模型调用的可执行操作/函数，可获取信息或改变外部状态 | 发送邮件、查询天气 | 可能产生副作用与安全风险，调用须经用户批准 [1][2][5] |
| **Resources（资源）** | 提供给 AI 应用的结构化/非结构化数据与文档，类似"只读文件" | 数据库记录、笔记、文件、API 响应 | 由客户端读取后作为上下文注入模型 [1][2][5] |
| **Prompts（提示）** | 预编写的提示词模板/工作流 | 代码审查提示模板 | 用于优化响应、确保一致性 [1][2][5] |

### 1.4 传输方式与架构优势

原生支持两种传输：本地场景的进程管道 STDIO，以及网络通信的 SSE+HTTP POST，并允许开发者自定义其他传输通道 [1]。架构上具备模块化（增删数据源只需启停对应服务器）、解耦（模型与数据源实现隔离）与双向通信三大优势；典型流程为初始化连接→发送请求→服务器处理→返回结果→断开连接 [1][4]。

## 二、MCP 解决了什么问题：设计初衷与核心痛点

### 2.1 起源：受 LSP 启发的"AI 版 USB-C"

MCP 由 Anthropic 工程师 David Soria Parra 与 Justin Spahr-Summers 创造：2024 年 7 月 David 提出想法，两人约一个半月完成协议与首次集成（Justin 主要负责 Claude Desktop 首次集成，David 在 IDE 中做概念验证）[9][13]。设计灵感直接来自 LSP（Language Server Protocol）——David 因需在 Claude Desktop 与 IDE 之间反复复制内容，意识到这是 M×N 问题，于是想把"AI 应用与扩展之间的通信"标准化 [9][13]。

### 2.2 三大核心痛点

1. **N×M 集成难题**：N 个 AI 客户端与 M 个外部工具/数据源在最坏情况下需构建维护 N×M 个独立连接器，各自处理认证、请求格式、错误处理与数据转换，开发量呈二次方增长，随生态扩张不可持续 [10][11][13]。
2. **工具接入碎片化与供应商锁定**：此前每个数据源都需定制连接器；各 LLM 提供商的 Function Calling/Tools API 互不兼容（如 OpenAI 与 Google 不兼容），切换模型需重写代码、复用率低 [7][11][12][13]。
3. **上下文割裂/信息孤岛**：LLM 知识止于训练数据截止日期，无法访问实时数据与企业内部数据库、文档仓库，也无法执行外部操作；手工粘贴信息进 prompt 随复杂度上升愈发困难 [7][8][10][12]。

MCP 因此被喻为"AI 应用的 USB 端口/USB-C"，以统一开放标准实现 LLM 与外部数据源、工具的无缝集成 [6][7][8][10][12]。

## 三、MCP 与既有方案的差异与互补

### 3.1 先厘清维度：各方案不在同一层面

RAG 是技术方案，Function Calling 是模型能力，ReAct 是推理范式，Agent 是系统角色，MCP 与 A2A 是通信协议，LangChain/LangGraph 是开发框架 [15][17]。因此"MCP 替代谁"的提法本身不准确，应看互补关系。

### 3.2 MCP vs Function Calling：互补而非替代

Function Calling 让 LLM 把自然语言指令转为具体 API 调用，解决模型知识更新停滞问题；但缺乏跨模型一致性、平台依赖强、扩展性有限，理论上仍需 M×N 次重复对接 [14][16][18]。MCP 以统一 JSON-RPC 2.0 标准化工具的发现、描述与调用，把 M×N 转化为 M+N，并支持一次注册多环境复用、安全隔离与权限配置 [15][16][17][18]。二者的关系可概括为：Function Calling 是"让模型知道有哪些工具可用"，MCP 是"定义工具如何被发现、描述和调用的统一标准"；MCP 负责整合工具资源，Function Calling 专注具体功能执行 [15][16]。

### 3.3 MCP vs A2A：手与协作网络

MCP 是 Agent 的"手"（连接工具，解决"做什么"），A2A 是 Agent 之间的通信协作协议（解决"与谁合作"）[17][18][19]。需注意业界也有观点认为 Agent 与 Tool 界限模糊，长期可能出现协议拉锯或融合统一 [19]。

### 3.4 与 RAG 的协同

RAG 在生成前从外部知识库检索并注入上下文，Function Calling 获取实时结构化数据并执行操作，二者可在医疗问答、投资建议等场景协同使用 [15][20]。

## 四、生态现状（截至 2026 年 11 月）

### 4.1 规范版本演进

| 时间 | 里程碑 |
|---|---|
| 2024-11-25 | Anthropic 发布 MCP 并开源 Python/TS SDK [11][22] |
| 2025-03-26 | 引入 Streamable HTTP + OAuth 2.1 [11][22] |
| 2025-11-25 | 重大更新：async tasks、extensions [11][22][25] |
| 2026-01-26 | 发布 MCP Apps 交互式 UI [11][22] |
| 2026-07-28 | 第 5 版规范（v2）：无状态架构、扩展框架、企业级安全；给出 12 个月弃用宽限期（弃用特性最早 2027-07-28 移除）[11][22][25] |

v2 的具体变化包括：移除协议级会话（Mcp-Session-Id）、GET 端点与 SSE 重投递，订阅推送改由 subscriptions/listen 承担 [35]。

### 4.2 治理与生态基础设施

2025-09 官方 MCP Registry 上线（提供 REST API 查询服务器元数据）；2025-12-09 协议捐赠给 Linux Foundation 并成立 AAIF；2026-03 发布 2026 路线图；2026-04-02 举办首届 MCP Dev Summit NYC [11][21]。

### 4.3 SDK 与客户端支持

四大 Tier 1 SDK（TypeScript、Python、Go、C#）已全面同步支持 2026-07-28 规范，Rust SDK 处于 Beta；Python 侧 FastMCP 框架最成熟，.NET 有 Microsoft 官方模板与 NuGet 包，Go/Java 早期为社区维护 [21][22][23][25][26]。客户端方面，Claude Desktop、Claude Code、ChatGPT、VS Code、Cursor、Windsurf、JetBrains 等主流 AI 应用与 IDE 均已支持；Agent 框架与平台方面，Microsoft Copilot（经 Semantic Kernel/Azure OpenAI）、LangChain、OpenAI Agents SDK 原生支持 MCP，Goose（Block）为 AAIF 创始项目之一 [11][21]。

**下载量数据存在口径差异**：有资料称 SDK 月下载量突破 4 亿 [22]，另有资料称 Tier 1 SDK 月下载接近 5 亿 [26]；TypeScript 与 Python SDK 累计下载量均超 10 亿次 [26]。本报告采信"4 亿量级"作为保守表述，理由是 4 亿与"接近 5 亿"可能分别对应不同统计窗口（如全 SDK 合计 vs 仅 Tier 1）或不同月份快照，且两者量级一致、不构成方向性冲突。

### 4.4 公开 MCP Server 数量：口径差异显著

各来源数字差异极大，需明确口径：

- 官方口径：Claude 应用商店已上架超 950 个服务器 [21]——这是**经官方审核上架**的数量，门槛最高。
- 第三方目录 Smithery：截至 2026-02 收录约 2,437 个 [21]。
- PulseMCP：17,520+ 条目 [21]——**收录条目**口径，可能包含重复、失效或非活跃项目。
- 其他资料：公开注册服务器超万个、总数 13,870+；发布后一季度早期约 5,000 个 [23][24][25]。

**采信建议**：讨论"可用、可信服务器"时采信官方商店 950+ 与 Smithery 2,437 的量级；讨论"生态规模/长尾"时采信 PulseMCP 的 17,520+ 条目口径。差异主要源于统计口径（审核上架 vs 目录收录 vs 注册总数）与时间点不同，而非数据矛盾。远程部署方面，自 2025-05 以来远程 MCP Server 数量增长近 4 倍，80% 热门服务器提供远程部署 [21]。

### 4.5 典型类别与应用场景

服务器覆盖数据库、版本控制、通信工具、云服务等领域；应用场景包括金融与医疗的实时数据连接、浏览器自动化、UI 界面创建、视频字幕提取等；生态伙伴如 Figma、Intuit、Netlify、Zoom 支持新版本 [21][22][24]。

### 4.6 企业采纳：预测与现实的落差

**预测（非事实）**：Gartner 预测 2026 年底 40% 企业应用将包含特定任务的 AI Agent（2025 年不到 5%），并预计 75% API 网关厂商与 50% iPaaS 厂商年底集成 MCP [21][22][24]。此为 Gartner 的预测，截至本报告日期尚未到验证时点。

**现实（已发生）**：MCP 已成为连接 AI 代理与数据库、SaaS 应用、内部服务的默认方式，但团队常在正式安全审查之外快速部署 MCP 服务器，安全团队往往不清楚这些服务器连接了什么、拥有什么权限，形成风险更高的"影子 IT"，多数组织尚未监控这一层 [29]。市场仍处早期：代理网关、静态扫描、秘密集成、异常检测等模式正在显现，但尚无主导平台，一些工具在实际负载下会崩溃 [29]。

## 五、企业落地的安全与治理争议

### 5.1 权限问题

MCP 处理工具权限存在诸多不足、权限界定模糊，而企业实际可用工具往往是有权限的；MCP 聚合权限跨越本不该连接的系统，一台被攻破的服务器可能暴露远超预期的范围；还存在代理权限超过用户权限的权限升级、以及不校验发起者身份导致的管理权限绕过 [27][29][30]。

### 5.2 授权规范争议

MCP 采用 OAuth 定义授权机制，但现行规范部分实现细节与现代企业实践冲突，业界正完善更新；MCP 的 authZ 规范在多用户企业部署中作用有限（MCP 服务器并非真正的资源服务器），多数 IdP 尚未实现 RFC 8707 资源指示器，不应盲目把用户访问令牌直接传给上游服务 [28][33]。

### 5.3 提示注入风险

可通过工具定义或返回数据进行提示注入；恶意 MCP 服务器可在描述字段、函数名、参数、错误信息中植入恶意指令（工具中毒），微软称之为间接提示注入；还有"AI 寄生攻击"（隐藏提示注入经人工客服转交 AI 助手）、工具遮蔽（Tool Shadowing）等形态 [28][29][30][31]。

### 5.4 供应链风险

MCP 服务器由可执行代码组成，谷歌可检索的 MCP 服务器目录已列出超过 15,000 个应用，但下载来源安全性未必可靠；服务器被信任后可通过更新植入恶意代码（"拉地毯"），需签名、SAST/SCA 扫描、依赖完整性验证与恶意软件扫描、加密服务器验证 [28][30][34]。

### 5.5 主要批评意见

MCP 设计时并非以安全为核心，却夹在 AI 代理与最敏感系统之间，错误爆炸半径过大；多数实现依赖静态凭证、明文 API 密钥，OAuth 采用率极低；Agent 的开放性使攻击面放大，"skill 像跑在没有任何防护的系统上的程序"，提示词注入后若授权 write 权限可能造成法律责任 [29][32]。

### 5.6 治理建议共识

对每个 MCP 服务器建立库存、执行最小特权（权限反映触发用户）、部署前扫描提示注入/不安全工具/凭证暴露、监控运行时行为并记录审计日志；在 tool 前加 gateway 与 DLP 防护、沙箱隔离、临时 token，并全链路 log 溯源；学术论文提出"五维控制 + Gateway"框架（认证授权、端到端溯源、上下文隔离与沙箱、在线策略执行、集中治理）[29][30][32][34]。

## 六、标准化进程与未来演进

### 6.1 已进入基金会治理（已发生）

Anthropic 与 OpenAI、Block 一起成立 Agentic AI Foundation，David 同时担任 MCP 核心维护者与基金会技术指导委员会（TSC）成员；基金会定位为"保护伞"，主要作用是保证项目中立性，MCP 技术治理本身没有本质变化 [37]。基金会的纳入原则是"从小开始"、协议层不重复维护同类协议：只承认 MCP 是已具备广泛采用度的事实标准，但若未来出现功能互补的成熟协议则保持开放 [37]。

### 6.2 当前限制（已发生）

工具定义虽支持动态注册（notifications/tools/list_changed），但多数实现仍以启动时静态注册为主；缺乏正式的智能体间通信标准；企业级特性（审计、SSO、网关）仍在规划中 [35]。

### 6.3 演进方向（规划与预测）

- **注册中心与认证**：官方 Registry 将构建集中式目录，提供签名验证与安全认证；认证已从本地 stdio 走向远程 MCP，2025 年 6 月为适配企业场景做了较大修订，并有 OAuth 标准专家参与 [36][37]。
- **多智能体协作扩展**：2025-11-25 版本引入长时间运行任务（long-running tasks）原语，用于支持深度研究类任务乃至 agent-to-agent 交互；采样（Sampling）允许服务器主动请求模型生成内容，支持模型间双向协作。官方表示接下来还有一两个关键原语和可扩展性问题待解决，之后协议将进入相对稳定阶段 [36][37]。
- **服务发现与网关**：当前 MCP Server 仍需用户手动查找配置，AI Agent 无法动态发现新 Server，未来可能推出服务注册与发现能力；网关将演变为集中管理平台，负责身份验证、授权、流量控制与工具路由 [24]。
- **外部标准化力量**：NIST 的 CAISI 于 2026-02-17 发起 AI Agent 标准化倡议，聚焦行业/国际标准话语权、开源协议社区发展、智能体安全与身份研究三大支柱 [35][38]。另有观点预测 Linux Foundation 等组织推动下 2026 年将出现统一的智能体协议标准框架，A2A 预计 2025 年底发布 1.0 正式版 [35][38]——后者为预测性表述，需注意其时间点已过，实际发布情况本笔记未提供，属资料缺口。

## 结论与建议

**总体结论**：MCP 用 JSON-RPC 2.0 + Host/Client/Server + Tools/Resources/Prompts 的简洁设计，把 AI 工具集成的 N×M 难题降为 N+M，已在两年内从 Anthropic 内部项目成长为经 Linux Foundation 治理、被主流 IDE/Agent 框架/云厂商广泛支持的事实标准 [1][2][10][11][21][37]。但"连接层标准化"已基本完成，"安全与治理层标准化"仍在进行中——权限模型、OAuth 企业适配、提示注入防护、供应链验证均无成熟共识 [28][29][30][33]。

**按场景的选择建议**：

1. **个人开发者/原型验证**：优先使用官方 Tier 1 SDK（TypeScript/Python）与 FastMCP，从官方 Registry 或 Smithery 选取高信誉服务器；注意 Tools 调用须保留用户批准环节 [1][21][22]。
2. **企业生产部署**：不要直接暴露 MCP Server。应建立服务器库存、执行最小特权、部署前做提示注入与凭证暴露扫描、运行时记录审计日志，并在 tool 前部署 gateway + DLP + 沙箱 + 临时 token [29][30][32][34]。对多用户场景，暂勿依赖 MCP 现行 authZ 规范，需自行补齐资源服务器侧校验 [33]。
3. **需要跨 Agent 协作**：MCP 负责"手"（工具连接），A2A 负责"与谁合作"，二者互补部署；但需关注两者边界模糊带来的长期协议拉锯风险 [17][18][19]。
4. **技术选型判断**：MCP 与 Function Calling 不是二选一——Function Calling 是模型能力，MCP 是工具发现与调用的标准层，应叠加使用 [15][16]。

**资料缺口说明**：本笔记未提供 A2A 1.0 的实际发布结果（原预测为 2025 年底），亦未提供 2026 年统一智能体协议标准框架是否落地的验证信息，相关判断只能停留在预测层面 [35][38]。
