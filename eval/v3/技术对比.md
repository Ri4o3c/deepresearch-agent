# LangGraph、CrewAI、AutoGen 多智能体框架选型研究报告

## 摘要

截至 2026 年 11 月，三个框架已形成清晰的差异化定位：LangGraph 以显式状态图为核心，在生产就绪度（持久执行、检查点、可观测性、人机协同）上领先，适合长时运行、需审计状态转换的复杂流程编排 [1][5][15]；CrewAI 以角色化协作抽象取胜，上手快、适合快速搭建团队式业务流程，但状态恢复与深度定制能力相对不足 [2][4][15][34]；AutoGen 擅长对话式、交互驱动的协作与快速原型，但已于 2026 年 2 月发布 1.0 后进入维护模式，微软将新开发转向 Microsoft Agent Framework（MAF），新项目不宜以其为首选 [7][9][10][12]。性能与成本实测显示 LangGraph 在延迟与 token 开销上最优，AutoGen 最高 [25]。综合结论：生产级复杂编排优先选 LangGraph，角色化快速交付选 CrewAI，AutoGen 仅建议用于存量维护或对话式原型，新项目应评估 MAF 或 AG2 [5][15][37]。

---

## 一、设计理念与核心抽象：三种截然不同的协作世界观

三个框架的差异根源在于它们对"多智能体如何协作"这一问题的不同回答。

**LangGraph——状态机/状态图。** 作为 LangChain 生态的重要组成部分，LangGraph 把 Agent 协作流程建模为图：节点（Node）是计算单元（Agent 或工具），边（Edge）代表流程走向，共享状态在图中流转，并原生支持循环、分支、检查点、中断与恢复 [2][3][6]。其核心抽象是"图 + 共享状态 + 路由条件"，提供对循环、分支、检查点与恢复行为的直接控制，适合长时运行或对操作敏感的系统 [1][5][6]。

**CrewAI——角色化协作。** CrewAI 受现实组织结构启发，把复杂任务分解，为每个 Agent 分配明确的角色（Role）、目标（Goal）和工具（Tools），再在结构化流程（Process）中接力完成任务，如同管理一个精英顾问团队或电影剧组 [1][2][4]。核心抽象是角色、任务、工具与流程（目前主要是顺序执行，也支持层级式流程），以 YAML 配置 + Python 装饰器定义 Agent 团队并编排成 Crew [2][4][6]。

**AutoGen——对话式协作。** AutoGen 由微软（研究院）开源，让多个 Agent 在群聊环境中通过对话、讨论甚至辩论共同解决问题，强调灵活性与可扩展性，用自然语言对话驱动协作，并允许人类直接参与 [2][4][5]。核心抽象是对话/消息，提供用户 Agent、助手 Agent、工具 Agent 等高级抽象及交互模式（如经理 Agent 分配任务给专家 Agent）；v0.4 重构引入异步消息通信与插件式组件 [1][3][4]。

> **选型含义：** 如果你的问题天然是"一张有分支和回退的流程图"，LangGraph 的抽象最贴合；如果是"几个固定角色按流程接力"，CrewAI 的表达成本最低；如果是"让 Agent 自由讨论出答案"，AutoGen 的对话模型最自然——但这一优势正被其维护状态所抵消（见下节）。

## 二、版本、维护状态与生态：格局已显著收敛

### 2.1 版本与维护状态

| 框架 | 最新版本/状态 | 维护状态 |
|---|---|---|
| LangGraph | 1.0 正式版 2025-10-22 发布；截至 2026 年 5 月核心为 1.1.x / SDK 0.3.14，另有资料记为 1.2.7 | 活跃维护 [7][9][10] |
| CrewAI | v1.14.4（2026 年 4 月）、v1.15.1 | 活跃维护 [7][9][10][14] |
| AutoGen | 2026 年 2 月发布 1.0 正式版后进入维护模式；另有资料称最新为 v0.7.5（2025 年 9 月）并自 2025 年底进入维护模式 | 仅缺陷修复与安全补丁，不再新增功能 [7][9][10][12][14] |

**关于 AutoGen 版本数字的差异说明：** 笔记中同时出现"2026 年 2 月 1.0 正式版"与"v0.7.5（2025 年 9 月）"两种说法。二者可能对应不同口径——前者或指 AutoGen 主线（AgentChat/Core）的 1.0 里程碑，后者或指某一子包或旧分支的最后版本；时间上 2025 年 9 月早于 2026 年 2 月，也符合"先有 0.7.5、后有 1.0"的演进顺序。本报告采信"2026 年 2 月发布 1.0 后进入维护模式"作为维护状态的判断依据，因为该结论在多个来源中一致出现 [7][9][10][12][14]，而具体版本号不影响选型结论。

### 2.2 社区活跃度与生态

- **LangGraph：** GitHub 星标约 3.2 万–3.61 万（2026 年 5–6 月），月下载量 3,450 万次；被视作生产级 Agent 的事实标准，公开案例包括 Klarna、Uber、LinkedIn、Rakuten、Elastic，并提供 LangGraph Cloud 托管执行与 LangSmith 可观测性 [7][9][10][11][13]。
- **CrewAI：** GitHub 星标约 5.1 万–5.46 万（2026 年 5–6 月）；月运行 4.5 亿次 agentic 工作流；企业能力含 FedRAMP High、专属 VPC、Microsoft Entra 与 Okta SSO、基于 Qdrant Edge 的运行时状态检查点；公开客户提及 Deloitte、PwC；内置搜索、代码解释器、文件读写等工具并支持自定义工具 [7][8][11][13]。
- **AutoGen：** GitHub 星标约 5.8 万–5.94 万（2026 年 5–6 月，三者中最高），微软内部与 Novo Nordisk 有披露使用 [9][10][11][13]。

**星标数与生产采用度的背离值得注意：** AutoGen 星标最高却已停止功能演进，LangGraph 星标最低却是公开生产案例最多、下载量最大的框架。这说明星标反映历史关注度而非当前工程价值，选型不应以星标为主要依据。

### 2.3 生态迁移信号

微软已将新开发转向 Microsoft Agent Framework（MAF 1.0，2026 年 4 月 GA），融合 AutoGen 与 Semantic Kernel，支持 YAML 定义、图工作流与检查点、原生 MCP/A2A；社区分叉 AG2（Apache 2.0）独立治理并持续开发 [9][10][11][13][14]。三者许可证均为 MIT（AutoGen 文档另用 CC-BY-4.0）；但均未内置多租户、成本归因与审计治理能力，企业级合规需自行补齐 [9][10]。

## 三、编排、状态、人机协同与可观测性：生产能力的核心分水岭

| 维度 | LangGraph | CrewAI | AutoGen |
|---|---|---|---|
| **编排模型** | 显式状态与边的底层图运行时（StateGraph），适合多决策点、并行处理与强定制 [5][16][18][22] | 基于角色的 Crew + 事件驱动 Flows（@start/@listen/@router 装饰器）[5][16][18][22] | 对话/事件驱动核心，强调自然语言交互与动态角色扮演 [5][16][18][22] |
| **状态管理** | 内置 checkpointing 与持久化/durable execution，每次状态转换自动保存，崩溃后可从断点精确恢复；DeltaChannel 只保存增量变更 [15][17] | 状态恢复与部分失败优雅恢复相对不足，更适合失败可重跑的低成本场景 [15][17] | 状态存储在消息历史中（每轮对话、每次工具调用、每次修订），灵活但确定性较低 [15][17] |
| **人机协同（HITL）** | 一等公民原语 interrupt_before / interrupt_after，可在命名节点暂停、交人工审核并从该点恢复，适合审批门与合规场景 [5][15][17][18] | 需用 Flows 的 @router 自行搭建"等待审批"状态，属自建模式而非原生原语 [5][15][17][18] | 通过 UserProxyAgent 或 human_input_mode 让人类随时介入对话，灵活但仅适合简单批准/拒绝门 [5][15][17][18] |
| **可观测性与调试** | 通过 LangSmith 提供企业级可观测性，支持节点级缓存（memory/SQLite 后端）与 LangGraph Studio 回放调试，可从任意检查点重放 [5][15][18] | 提供带内置错误处理的综合缓存工具，但资料未提及其专门的调试/回放工具 [5][15][18] | tracing 相对薄弱，虽有 OpenTelemetry 风格插桩但覆盖有限 [5][15][18] |

**总体定位：** LangGraph 在生产就绪度（持久执行、检查点、可观测性、HITL）上领先，适合长期运行、有状态、需审计状态转换的工作流；CrewAI 适合快速部署的角色化业务流程与低失败成本场景；AutoGen 擅长对话式、交互/评审驱动与快速原型，但 AG2 重设计尚未到稳定 v1.0，生产成熟度仍需提升 [5][15][16][22]。

## 四、性能、成本与可靠性：实测数据与口径辨析

### 4.1 延迟实测（研究任务）

LangGraph 中位端到端延迟 14.1s、P95 19.8s；CrewAI 18.4s / 31.2s；AutoGen 22.7s / 41.5s。代码审查任务中位延迟分别为 8.3s、9.1s、11.6s；客户分流任务 10.2s、11.7s、14.9s；数据管道任务 20.4s、24.8s、31.3s。在 6-agent 数据管道任务上，AutoGen 中位延迟比 LangGraph 高 53% [25]。

延迟差异有结构性原因：LangGraph 在请求首个 token 前就把 agent 图编译为确定性执行计划；CrewAI 在运行时通过顺序任务管理器解析 agent 委派，带来同步开销；AutoGen 的对话式协调模型在 agent 数量增加时开销显著，agent 花 token 协商下一步而非执行 [25]。

### 4.2 成本实测（GPT-4o）

每 1000 次研究任务：LangGraph $41.70、CrewAI $48.20、AutoGen $67.40；每 1000 次代码审查任务分别为 $17.30、$19.80、$26.10。相对原始 API 调用的 token 开销：LangGraph +9%、CrewAI +18%、AutoGen +31%。另有基准显示 3 步任务按每日 1000 次运行计，LangGraph 约 $63/月，CrewAI $78–$102，AutoGen $84–$171 [25][28]。

### 4.3 多组数据的口径差异说明

笔记中存在三组量级不同的性能/成本数据，需明确区分：

1. **agent-harness 实测（秒级延迟、美元级成本）** [25]：这是唯一给出完整任务矩阵与结构性归因的实测，本报告以其为主要采信依据。
2. **GAIA 基准公开运行** [26]：AutoGen 8.41s / 1,381 tokens；CrewAI 11.87s / 17,058 tokens；LangChain 12.86s / 7,753 tokens；LangGraph 未纳入该次发布运行。**注意**：该组数据中 AutoGen 延迟最低、token 最少，与 [25] 结论方向相反。可能原因是 GAIA 任务形态偏单轮问答、agent 数量少，对话式协调的开销优势得以体现；而 [25] 的多 agent 长流程任务放大了 AutoGen 的协商成本。此外该组对比对象是 LangChain 而非 LangGraph，口径不完全对齐。资料同时指出 token 效率往往比框架自身开销更主导成本 [26]。
3. **建模估算（非实测）** [27]：平均延迟 LangGraph 2,340ms、CrewAI 2,890ms、AutoGen 3,120ms；P95 4,200 / 4,950 / 5,800ms；token 开销约 8% / 12% / 15%；每次执行内存 45MB / 52MB / 78MB。资料明确其为量级参考，并强调单轮层面三者基本持平、往返延迟由 LLM API 调用主导，AutoGen 初始化最快、CrewAI 进程预热最重（serverless 冷启动成本需注意）[27]。

**采信结论：** 在**多 agent、长流程**场景下采信 [25] 的排序（LangGraph < CrewAI < AutoGen）；在**单轮/少 agent** 场景下三者差距显著缩小，[26][27] 均支持"框架开销不是成本主导因素"的判断。选型时应以自身任务形态（agent 数量、轮次深度）为基准做小规模实测，而非直接套用任一基准。

### 4.4 可靠性与容错

LangGraph 以状态机与检查点实现状态回溯与恢复，支持状态持久化、时间旅行、错误恢复，但大模型调用容错需结合外部工具；AutoGen 具备重试、降级策略、超时控制、错误处理与沙箱执行；CrewAI 支持重试但降级策略需自定义，为任务级容错、部分上下文保持。复杂任务完成率 LangGraph 约 62%、AutoGen 约 58%、CrewAI 约 54%（DataCamp 测试），在需要错误恢复与状态管理的任务上差距更大 [29][15]。

### 4.5 部署成本与扩展性

自托管时 AutoGen 与 CrewAI 为 $0（CrewAI 云版 $25/月），LangGraph 自托管 $0、含 LangSmith $39/月；5 人团队 CrewAI $99–$500/月、LangGraph LangSmith 席位 $195/月；20 人企业 LangGraph 最低 $780/月 [15]。LangGraph 支持并行执行、内置 LangSmith（工作流可视化、跟踪评估、人工干预），但复杂图结构可能带来额外计算开销、学习曲线陡峭；CrewAI 可观测性集成 Langfuse、W&B Weave、Datadog 等；AutoGen 集成 AgentOps、Langfuse、MLflow，支持成本分析与延迟跟踪 [27][29][33]。

> **成本口径提示：** 框架许可费（多为 $0）与平台服务费（LangSmith、CrewAI 云版）是两笔账；上表月费差异主要来自可观测性/托管平台而非框架本身，选型时应把平台费与自建可观测性的人力成本一并计入。

## 五、典型场景适配性与已知局限

- **AutoGen** 适合需要高度定制化和灵活对话的场景，其强大的可编程性使其能够处理各种复杂的协作需求；但局限是要求开发者具备较强的技术能力 [34]。
- **LangGraph** 适合需要精确流程控制和状态管理的场景，其图结构工作流和状态管理机制使其在处理复杂业务逻辑（如复杂流程编排）时具有优势；但局限是学习成本相对较高 [34]。
- **CrewAI** 适合需要快速搭建团队协作系统（角色化协作）的场景，其高级抽象和简洁接口使其易于上手；但局限是在复杂定制需求方面可能存在不足 [34]。

**资料不足说明：** 关于"开放式多轮对话/研究型任务"这一场景，笔记仅给出三个框架的总体适配性与局限，**未针对该场景逐一说明各框架的具体表现**；仅泛泛指出多轮对话场景对历史指令遵循一致性、长程记忆、目标拆解与外部交互适配性等能力要求较高 [34][35]。此外，笔记中关于协作拓扑（顺序式、层级式、联合协作式、混合式）的适用场景与风险（如顺序式缺乏反馈修正、联合协作式易跑题且 Token 消耗高）属于通用架构层面，**未与三个具体框架对应** [36]。因此本报告不对"研究型任务"给出框架级排序结论，建议读者以第四节的任务形态实测方法自行验证。

## 六、2026 年演进趋势对选型的影响

**MCP 标准化已高度普及。** 截至 2026 年 3 月，10 个主流框架中至少 8 个原生支持 MCP，MCP 正成为 Agent 工具调用的"USB 接口"，框架间工具互操作壁垒正在消失。因此选型时"工具生态丰富度"的权重应下降，因为 MCP 工具可在任何框架中使用 [37]。

**A2A 普及速度不及 MCP。** 目前原生支持 A2A 的框架仅 Microsoft Agent Framework、Google ADK、AgentScope，CrewAI 和 LangGraph 通过社区插件提供部分支持；A2A 的真正价值在跨组织 Agent 互操作，但需要更长的采纳周期，因此不应把 A2A 支持作为近期选型的决定性因素 [37]。

**格局从爆发走向收敛。** 2026 年是多 Agent 系统进入生产环境的关键年份，这一转变依赖协议成熟度和收敛性；MCP、ACP、A2A、AG-UI、A2UI 等标准化协议的推广将实现不同厂商 Agent 间的互操作性 [38][39]。框架格局已从 2024 年的"寒武纪大爆发"（GitHub 上 1000+ Stars 的 Agent 仓库从 14 个增至 89 个，增长 535%）走向显著收敛，存活者各自占据清晰生态位；MCP 标准化、A2A 兴起、Context Engineering 理念普及正在重塑框架竞争的底层逻辑 [37]。

**选型逻辑转向生态绑定与场景匹配：** 云厂商生态（Azure→Microsoft Agent Framework、Google Cloud→Google ADK、阿里云→AgentScope）、自托管/私有化（Dify 最成熟或 Agno）、模型偏好（OpenAI 生态→OpenAI Agents SDK 或 LangGraph、Gemini→Google ADK、国内模型→AgentScope 或 Dify、模型无关→PydanticAI 或 LangGraph）[37]。协议支持已成为框架横向对比的显式维度：PydanticAI 原生支持 MCP，LangGraph、Agno 支持 MCP，CrewAI 为社区适配，MetaGPT 使用内部协议；同时 2026 年企业生产准入还要求 AgentOps 全链路治理、状态机与持久化、多代理零信任安全围栏三大支柱 [40]。

## 结论与建议

### 核心结论

1. **三者已不是同一赛道的竞争关系。** LangGraph 是"底层图运行时"，CrewAI 是"角色化业务编排层"，AutoGen 是"对话式协作实验平台"且已停止功能演进 [5][15][16][22][12]。选型应先确定问题形态，再匹配框架。
2. **生产就绪度排序明确：LangGraph > CrewAI > AutoGen。** 差距集中在持久执行、检查点恢复、原生 HITL 与企业级可观测性四项 [15][17][18]。
3. **性能与成本排序（多 agent 长流程）：LangGraph 最优，AutoGen 最差。** 但单轮/少 agent 场景差距收窄，框架开销非成本主导 [25][26][27]。
4. **AutoGen 不宜作为新项目首选。** 已进入维护模式，微软新开发转向 MAF，社区分叉 AG2 尚未到稳定 v1.0 [7][9][10][12][14]。

### 按场景的选择建议

| 场景/条件 | 推荐 | 理由与注意事项 |
|---|---|---|
| 复杂流程编排、长时运行、需审计状态转换、合规审批门 | **LangGraph** | 检查点、durable execution、interrupt_before/after 原生支持；LangSmith 可观测性 [15][17][18]。需接受较陡学习曲线与复杂图的计算开销 [27][29][34] |
| 角色化协作、快速交付、失败可重跑的低成本业务流程 | **CrewAI** | Role/Goal/Backstory + Crew 上手快，企业能力（SSO、FedRAMP High）较完整 [2][4][8][34]。需自行搭建审批状态与降级策略 [15][17] |
| 对话式原型、交互/评审驱动的研究探索 | **AutoGen（仅限存量或原型）** | 对话模型自然、可编程性强 [34]。但维护模式意味着无新功能，长期项目应评估迁移至 MAF 或 AG2 [12][14] |
| 新项目且已绑定 Azure / 需要 AutoGen 能力 | **Microsoft Agent Framework（MAF）** | MAF 1.0 于 2026 年 4 月 GA，融合 AutoGen 与 Semantic Kernel，原生 MCP/A2A [9][10][11][13] |
| 模型无关、需最大灵活性 | **LangGraph** | 被列为模型无关选项之一 [37] |
| 工具生态是主要考量 | **三者差异已不大** | MCP 普及使工具可在任何框架复用，应降低该维度权重 [37] |

### 可操作的选型步骤

1. **先定形态**：画出你的协作拓扑（顺序/层级/联合/混合），若含分支回退与人工审批门，直接倾向 LangGraph [36][15]。
2. **再做小规模实测**：以自身任务形态（agent 数量、轮次深度）跑延迟与 token 基准，不要直接套用任一公开基准——[25] 与 [26] 的结论方向相反正说明任务形态的决定性作用 [25][26]。
3. **核算总成本**：把框架许可费（多为 $0）、平台服务费（LangSmith $39/月起、CrewAI 云版 $25/月起、企业档 $780/月起）与自建可观测性人力一并计入 [15]。
4. **补齐治理缺口**：三者均未内置多租户、成本归因与审计治理，企业级合规需自行补齐，并按 2026 年生产准入要求覆盖 AgentOps 治理、状态机持久化、零信任安全围栏三大支柱 [9][10][40]。
5. **锁定退出路径**：优先选择支持 MCP 的框架以保留工具层可迁移性；A2A 暂不作为决定性因素 [37]。

### 资料缺口提示

本报告未能就"开放式多轮对话/研究型任务"给出三框架的逐一对比结论，因笔记仅提供总体适配性描述而未覆盖该场景的具体表现 [34][35]；协作拓扑与具体框架的对应关系亦缺失 [36]。建议在正式选型前针对该场景补充实测。
