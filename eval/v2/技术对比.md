# LangGraph、CrewAI、AutoGen 多智能体框架选型研究报告

## 摘要

三者并非同一层面的竞品，而是三种不同的编排范式：LangGraph 是状态机式的图编排框架，CrewAI 是角色化任务接力框架，AutoGen 是对话驱动的多智能体框架 [1][2][3]。选型的核心判断依据是工作流的复杂度与可控性要求：复杂、长时运行、需要审计与中断恢复的生产系统应选 LangGraph；需要快速搭建角色分工型原型、流程相对线性的场景应选 CrewAI；以多智能体自由对话、研究探索为主的场景可考虑 AutoGen [22][24][30][34]。但必须注意，AutoGen 已进入维护模式，微软官方推荐新项目转向 Microsoft Agent Framework（MAF），因此 AutoGen 不应作为新项目的长期技术底座 [6][7][8]。此外，2026 年 A2A 等互操作协议的标准化，使"生态归属"和"协议兼容性"成为与框架能力同等重要的选型维度 [37][38]。

---

## 一、三个框架的定位与架构范式

### 1.1 三种范式，三种取舍

| 框架 | 定位 | 核心设计理念 | 架构模型 |
|---|---|---|---|
| **LangGraph** | LangChain 团队发布的状态驱动任务流框架 | 显式状态管理、灵活流转控制，构建有状态、可回溯、具复杂循环逻辑的 Agent 系统 [3][4] | 图式编排（状态机）：节点为 Agent 状态或操作，边为状态转换，支持条件执行、循环回溯、检查点与基于状态的记忆 [1][2][3] |
| **CrewAI** | 开源 Python 多智能体编排框架 | 「角色化协作」：为每个 Agent 赋予角色（Role）、目标（Goal）和工具（Tools），像管理精英顾问团队一样在结构化流程中接力完成任务 [2][3][5] | 角色协作式「Agent-Task」模型：核心要素为角色、任务、工具与流程（目前主要是顺序执行），Agent 间通过任务传递而非即时对话协作 [1][2][3] |
| **AutoGen** | 微软（研究院）开源的多智能体对话框架，支持 Python 与 .NET | 「对话式协作」：多个可定制的可对话 Agent（含人类）通过消息传递、讨论甚至辩论协作，强调代码执行和验证 [2][3][5] | 对话驱动模型：提供用户 Agent、助手 Agent、工具 Agent 等抽象及「经理分配—专家处理—汇总」等交互模式；v0.4 重构引入异步消息通信、插件式组件与跨语言协同 [1][2][5] |

### 1.2 范式差异带来的直接后果

- **控制力 vs 灵活性的权衡**：LangGraph 的显式图结构提供最强的流程控制与持久化能力 [1][2][3]；CrewAI 因 Agent 间靠任务传递协作，灵活性较低、难以处理动态分支或循环 [1][2][3]；AutoGen 输出更灵活，但稳定性依赖对话编排方式 [1][2][5]。
- **心智模型成本**：CrewAI 的"角色团队"隐喻最贴近人类组织直觉，LangGraph 的 StateGraph 概念学习曲线最陡 [30][34]。

## 二、版本演进、维护活跃度与生态现状（截至 2026 年 11 月）

### 2.1 AutoGen：已进入维护模式，这是选型的决定性事实

- AutoGen 已于 **2025 年 10 月**进入维护模式，不再接收重大功能更新，微软官方推荐新项目改用 Microsoft Agent Framework（MAF）[6][7][8]。**注意口径差异**：另有资料称进入维护模式的时间为 2026 年 4 月 [6][7][8]。本报告采信"2025 年 10 月"作为维护模式起点，理由是同一批资料中"AutoGen 与 Semantic Kernel 于 2025 年 10 月宣布合并为 MAF"的表述与之相互印证 [32][35]；"2026 年 4 月"更可能是 MAF 1.0 GA 的时间点被混记。
- **MAF 1.0 于 2026 年 4 月 GA**，是 AutoGen 与 Semantic Kernel 的合并体，具备 YAML agent 定义、带 checkpointing 的图工作流、原生 MCP 与 A2A 协议支持，并承诺长期支持（LTS）[6][7][8]。另有资料称 MAF 于 2026 年 2 月达到 RC 状态 [32][35]，与 4 月 GA 并不矛盾（RC 在前、GA 在后）。
- **社区分支 AG2**（Apache 2.0）在独立治理下继续活跃开发，2026 年 5 月发布 v0.12.2，但用户基数小于主框架，且尚未达到稳定 v1.0、缺乏已验证的生产部署 [6][8][9]。

### 2.2 LangGraph：架构深度 + 生态纵深

- 2026 年推出 **Deep Agents**——图运行时之上的更高层抽象，内置规划、子代理管理，默认 agent 轮次输入 token 减少 65% [6][9][11][12]。
- 生态优势包括 LangSmith 可观测性、LangGraph Cloud 托管执行与内置状态持久化，背靠 LangChain 生态（LangChain 有 90,000+ GitHub 星标）[6][9][11][12]。

### 2.3 CrewAI：商业化与企业能力推进最快

- 每月跨过 **4.5 亿次 agentic workflow**；企业能力新增 FedRAMP High、专用 VPC、通过 Microsoft Entra 与 Okta 的 SSO，以及由 Qdrant Edge 支持的运行时状态 checkpointing [6][7][10]。
- **GitHub Star 数据存在口径差异**：不同资料给出 50.8k 与 57,217 两个数字 [6][7][10]。本报告采信"约 5 万余星标、为四大框架中社区热度最高者"的定性结论，不采信单一精确数字，因为两个来源均未说明统计时点，差异很可能来自抓取时间不同。

### 2.4 社区规模的解读陷阱

AutoGen 的 GitHub 星标数在三者中最多，但反映的是多年累积的历史采用量而非当前选型建议；LangGraph 星标最少但架构深度最强，CrewAI 居第二且路线图活跃 [10]。**星标数不能作为选型依据**，尤其对已进入维护模式的 AutoGen 而言。

## 三、能力维度对比：状态管理、协作模式、人机协同与可观测性

> **资料缺口说明**：现有资料未提供针对 LangGraph、CrewAI、AutoGen 三者在状态管理、协作模式、HITL、可观测性四个维度上的严格横向对比表——[8] 的目录中出现"三大框架多维对比""框架特性详细对比"等标题，但正文内容缺失 [18]。以下仅能基于零散信息给出有限判断，并明确标注缺口。

### 3.1 状态管理

- **LangGraph**：检查点（Checkpoints）与基于状态的记忆是其架构内建能力，提供最强的持久化能力 [1][2][3]；基于 Google Pregel 图计算模型，适合长时间运行、可中断恢复的复杂系统 [32][35]。
- **CrewAI**：2026 年新增由 Qdrant Edge 支持的运行时状态 checkpointing [6][7][10]，属于后补能力。
- **AutoGen**：资料未给出其状态管理能力的具体描述，**资料不足**。

### 3.2 多智能体协作模式

- 通用层面，多智能体协作可分为**基于角色**（按组织框架赋予角色、权限与目标，利于任务分解与模块化，但灵活性和整合依赖存在挑战）与**基于模型**（智能体建立关于自身状态、环境与其他智能体的概率性或学习型内部模型，灵活但复杂度和计算成本高）两类 [16]。CrewAI 明显属于前者，AutoGen 的对话辩论更接近后者。
- 资料中关于 OpenAI Swarm 与 LangChain 协作模式的描述 [16] 并非针对本报告三个框架，**不作为三方对比依据**。

### 3.3 人机协同（HITL）

- HITL 涵盖人类监督（日志审查、实时仪表盘）、干预与纠正、人类反馈用于学习（如 RLHF）、决策增强、人机协作与升级策略；其变体 Human-on-the-loop 由人类制定总体策略、AI 负责即时执行 [15]。
- 资料提到 ADK 可识别需人工审核的场景并启动升级流程、LangChain 也提供相关工具，但**未给出三个框架 HITL 能力的量化或逐项差异** [15]。**资料不足**。

### 3.4 可观测性与调试

- 资料仅给出通用建议而非框架间差异：应保证 trace/span 命名与字段语义一致、可导出或接收 OTLP、评估结果能回写到 trace、线上 Bad Cases 可沉淀为离线回归集；到 2026 年主流产品差异越来越集中在"分析体验"和"协作能力"，底层追踪模型向 OTel 语义靠拢，Langfuse、LangSmith 与内部平台均适用 [14]。
- 可确认的事实是：LangGraph 有原生配套的 LangSmith 可观测性 [6][9][11][12]；CrewAI 与 AutoGen 在资料中无对应的可观测性产品描述，**资料不足**。

## 四、性能、成本与生产部署

### 4.1 性能实测

在 **107 个真实数据工程任务的基准测试**中，LangGraph 通过率最高（97/107），延迟与 token 消耗更低；CrewAI 的 token 消耗和延迟更高；AutoGen 在有状态多步操作上表现吃力、频繁失败 [24]。

在复杂工作流场景中，LangGraph 的"有状态循环 + 条件分支"把长链任务失败率从 CrewAI 的 12% 压到 4% 以下；IDC 2025 年 5 月压力测试显示，256 节点任务网中 LangGraph 节点间延迟 P99 稳定在 270ms，而 CrewAI 同场景飙升到 1.1s [30][31][34]。

### 4.2 成本控制

AutoGen 的对话式模式每个任务通常产生 **20+ 次 LLM 调用**（因智能体相互辩论与迭代输出），推高调用成本；LangGraph 的显式图控制流被认为更可靠且更具成本效率 [22][24]。LangGraph 的 Deep Agents 抽象还将默认 agent 轮次输入 token 减少 65% [6][9][11][12]。

### 4.3 生产部署与可扩展性

- **LangGraph**：面向有状态、长时间运行工作流的低层编排框架，据 LangChain 仓库称已在 Klarna、Replit、Uber、LinkedIn 等生产环境使用 [25]。对复杂工作流，图式编排比对话式模式扩展性更好，因为可显式定义执行路径；其 MCP 工具服务器可作为图节点集成，对工具密集型系统是显著优势 [22]。
- **CrewAI**：以角色化心智模型和最快的多智能体原型见长。**需谨慎对待的说法**："美国财富 500 强中 60%"来自公司新闻稿样板文字，未经独立审计 [25]，不应作为选型证据。
- **AutoGen**：微软已宣布其主要用于原型与研究，生产部署推荐转向 MAF，但 MAF 成熟度仍有限 [24][28]。

### 4.4 已知局限

- **LangGraph**：引入类型化状态 schema、节点签名、图拓扑等维护开销，对真正复杂的多智能体工作流才值得 [24][28]；学习曲线最陡，同样"搜索→摘要→决策"流程 LangGraph 需 140 行、CrewAI 仅 60 行 [30][31][34]。
- **CrewAI**：工具链扩展目前只有官方维护的 20 余种，遇冷门 API 需自行封装；单线程架构导致高并发时延迟明显，中等复杂度任务够用 [30][32][34]。
- **AutoGen**：生产环境需额外封装 API 网关，不适合零基础团队，企业级代码生成场景需先验证沙箱逃逸风险 [30][31][34]。

## 五、按场景的选型建议与真实反馈

### 5.1 场景矩阵

| 场景 | 首选 | 关键依据 |
|---|---|---|
| **复杂工作流编排** | LangGraph | 失败率从 CrewAI 的 12% 降至 4% 以下；256 节点 P99 延迟 270ms vs CrewAI 1.1s [30][31][34] |
| **快速原型** | CrewAI | 开发效率单项评分 4.2/5；定义 Agent 仅需五行代码；微软亚洲研究院 2025 年 4 月内部黑客松中，CrewAI 团队平均 3.2 小时跑通"三角色协作"Demo，原生 LangChain 团队需 9.5 小时 [30][31][34] |
| **多轮对话协作 / 多 Agent** | AutoGen（限研究/原型） | 天然支持多 Agent 且有可视化；arXiv 2025 上半年 Agent 相关论文中 38% 的实验部分直接引用 AutoGen [30][31][34] |
| **企业级生产系统** | LangGraph | 状态管理与持久化执行能力，适合长时间运行、可中断恢复的复杂系统 [32][35] |

### 5.2 一条可操作的复杂度分界线

业内经验：**节点数 < 20 用 CrewAI，> 50 直接上 LangGraph**；LangGraph 适合需要审计追踪的金融/医疗场景，建议先画 Mermaid 图再写代码 [30][34]。

### 5.3 需要警惕的反馈

- CrewAI 过去 90 天 GitHub 新增 Star +9.4k，超过 LangGraph（+6.7k）与 AutoGen（+4.1k）之和 [30][31][34]，说明其社区动能强，但这与"生产级复杂编排能力"是两回事。
- AutoGen 学术引用领先不等于工程可用，其维护模式状态是硬约束 [6][7][8]。

## 六、2025–2026 趋势对选型的影响

- **市场格局**：2026 年是 AI Agent 从实验室概念迈入工业级应用的关键转折点，市场形成科技巨头（60%+ 份额）、AI 原生企业（约 25%）、垂直行业服务商（约 15%）三大阵营竞合格局，选型需考虑阵营生态归属 [36]。
- **协议标准化**：A2A 协议通过标准化智能体交互，为多智能体系统提供类似人类团队的协作框架，互操作标准化成为选型的新维度 [37]。MAF 已原生支持 MCP 与 A2A [6][7][8]，LangGraph 的 MCP 工具服务器可作为图节点集成 [22]。
- **四维评估框架**：多智能体协作平台选型需评估编排灵活度、通信协议标准化程度、异构系统集成能力和治理审计机制，只有同时满足四项才能支撑生产级部署 [38]。
- **场景化矩阵已成主流**：选型指南已按场景给出首选/备选框架矩阵（如企业级生产系统首选 LangGraph、备选 AgentScope 与 Google ADK；多智能体团队协作首选 MetaGPT、备选 CrewAI 与 AG2），说明框架融合与并存使选型更依赖具体场景而非单一最优解 [36]。
- **选型难点转移**：2026 年 Agent 框架爆发式增长、100+ 框架并存，选型难点已从"知道有哪些框架"转为"建立清晰理性的选型思路"，需从架构范式、决策树和隐性成本等底层视角评估 [33][39]。

> **资料缺口说明**：关于"框架融合"的具体机制、协议标准化的技术细节以及 2025 年趋势的论述较为有限，现有资料主要聚焦 2026 年现状与选型方法，无法充分支撑对融合路径的深入判断 [36][33][37][38][39]。

## 结论与建议

### 核心结论

1. **三者不是同一层面的替代品**，而是图编排、角色协作、对话驱动三种范式的代表 [1][2][3]。选型应先确定工作流形态，再选框架。
2. **AutoGen 不应作为新项目的长期底座**。它已于 2025 年 10 月进入维护模式，微软推荐新项目转向 MAF [6][7][8]；MAF 1.0 已于 2026 年 4 月 GA 并承诺 LTS [6][7][8]。若团队已深度使用 AutoGen，迁移路径是 MAF（Azure 生态）或 AG2（社区分支，但尚未达稳定 v1.0、缺乏已验证生产部署 [6][8][9]）。
3. **LangGraph 在复杂生产场景的优势有实测支撑**：107 任务基准通过率 97/107、失败率 <4%、256 节点 P99 延迟 270ms [24][30][31][34]。代价是学习曲线与维护开销 [24][28]。
4. **CrewAI 是原型效率的最优解，但不是高并发复杂编排的最优解**：单线程架构、20 余种官方工具、高并发延迟明显 [30][32][34]。

### 按条件的操作建议

- **若节点数 > 50、需要审计追踪、长时运行与中断恢复（金融/医疗/企业核心系统）** → 选 **LangGraph**；先画 Mermaid 图再写代码 [30][34]，并配套 LangSmith 做可观测性 [6][9][11][12]。
- **若节点数 < 20、目标是 1–3 天内跑通角色分工 Demo 或中等复杂度业务流** → 选 **CrewAI**；但需提前评估冷门 API 的工具封装成本与并发上限 [30][32][34]。
- **若核心需求是多智能体自由对话、辩论、研究探索或学术复现** → 可用 **AutoGen 做原型**，但**不要将其作为生产长期方案**；生产化时迁移至 MAF（Azure 生态）或评估 AG2 [6][7][8][9]。
- **若处于 20–50 节点的模糊区间** → 以"是否需要条件分支与循环"为二次判据：需要则 LangGraph，纯线性接力则 CrewAI [1][2][3][30][34]。
- **无论选哪个**，都应将"通信协议标准化程度（MCP/A2A 支持）"与"治理审计机制"纳入评估，这是 2026 年生产级部署的四项必要条件之一 [38]；同时优先选择能导出 OTLP、trace 语义与 OTel 对齐的方案 [14]。
