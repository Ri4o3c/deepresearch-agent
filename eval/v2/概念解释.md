# MCP（Model Context Protocol）协议研究报告

## 摘要

MCP 是由 Anthropic 于 2024 年 11 月 25 日发布并开源的开放协议，用于标准化 LLM 应用与外部数据源、工具之间的集成，其核心价值是把 N 个 AI 客户端与 M 个工具之间的 N×M 定制连接问题降为 N+M 的一次性适配 [8][9][12]。协议基于 JSON-RPC 2.0，采用 Host/Client/Server 三角色架构，服务端提供 Resources、Tools、Prompts 三类原语，传输上支持 STDIO 与 HTTP（2025 年 3 月起以 Streamable HTTP 取代早期 SSE 方案）[1][2][3]。截至 2026 年，MCP 已从 Anthropic 的单一项目演化为行业级标准：规范经历多轮重大修订（最新为 2026-07-28 的无状态化大改），四大 Tier 1 SDK 全面同步，Claude、ChatGPT、Cursor、VS Code 等主流客户端接入，公开注册服务器超过一万个，协议亦于 2025 年 12 月捐赠给 Linux Foundation [8][21][22][23]。但生态繁荣的同时，安全（提示注入、工具投毒、供应链风险）、认证授权规范与企业级运维能力仍是主要短板，官方与业界正通过 OWASP 风险清单、OAuth 授权演进、注册中心与网关方案加以应对 [25][27][28][31]。总体判断：MCP 已成为 Agent 调用外部工具的事实通用接口，但企业规模化落地仍处于"能力追赶"阶段 [8][24]。

---

## 一、MCP 是什么：技术定义与核心架构

### 1.1 定义与协议基础

MCP 是一个开放协议/开放标准，为 LLM 应用与外部数据源、工具之间的无缝集成提供标准化方式，使应用能与语言模型共享上下文、向 AI 系统公开工具和功能、构建可组合的集成与工作流 [2][3][4]。协议使用 JSON-RPC 2.0 建立通信，具有有状态连接，并进行服务端与客户端之间的功能协商；消息分为请求（带唯一 ID）、响应（含结果或错误）和通知（无需回复）三类 [1][2]。

### 1.2 三角色架构

| 角色 | 职责 | 典型实例 |
|---|---|---|
| **Host（主机应用）** | 发起连接的 LLM 应用，内部集成 MCP Client，管理与一个或多个 Server 的连接 | Cursor、Claude Desktop、VS Code、ChatGPT、Cline [1][2][3] |
| **Client（客户端）** | 在 Host 内运行，与 Server 保持 1:1 连接，负责建立连接、发送请求、接收响应与通知，并在 Host 需求与协议之间做翻译 | 一个 Host 可运行多个 Client 连接多个 Server [1][3][6] |
| **Server（服务器）** | 独立运行的轻量程序，是能力的实际提供者，通常聚焦单一集成点 | GitHub、PostgreSQL、Playwright、Figma Server [1][3] |

### 1.3 服务端原语与客户端能力

服务端提供三类原语 [1][2]：

- **Resources（资源）**：结构化数据或文档内容，供客户端读取并作为模型上下文，类似"只读文件"，如数据库记录、用户笔记。
- **Tools（工具）**：可被模型调用的可执行操作或函数，可获取信息或改变外部状态（如发邮件、查天气）。工具代表任意代码执行，Host 必须获得用户明确同意后才能调用。
- **Prompts（提示）**：预编写的提示词或模板化消息与工作流，可插入模型输入以影响其行为，如"代码审查提示模板"。

客户端侧则可向服务端提供 **Sampling**（服务端发起的代理行为与递归 LLM 交互），以及配置、进度跟踪、取消操作、错误报告、日志记录等辅助能力 [2]。

### 1.4 传输方式与规范版本

传输上原生支持 **STDIO**（进程标准输入输出，适合本地场景）与基于 HTTP 的传输；早期方案为 SSE + HTTP POST，2025 年 3 月规范引入 **Streamable HTTP** 取代之，Server 提供统一 HTTP 端点同时支持 POST 与 GET，并可选择性使用 SSE 流式传输，同时允许自定义其他传输通道 [1][3]。

规范版本演进包括：2024-11-05（初始稳定版）、2025-03-26、2025-06-18（移除 JSON-RPC batching、引入结构化工具输出等）、2025-11-25（含 OpenID Connect Discovery、增量范围授权、实验性 Tasks 等）[2][7]。需注意，笔记中另有一份资料给出的版本时间线与此不同（见第三章），两者口径差异将在 3.1 节说明。

### 1.5 安全与信任原则

规范明确：用户必须对所有数据访问和操作明确同意并保留控制权；Host 在向服务端暴露用户数据前须获得明确同意；工具的行为描述（如注解）应视为不可信，除非来自可信服务端 [2]。

## 二、MCP 解决了什么问题：设计动机与痛点

### 2.1 提出主体与时间

MCP 由 **Anthropic 于 2024 年 11 月 25 日发布并开源**，配套发布正式规范、SDK 与参考实现 [8][9][10][11][12]。多份资料在时间与主体上相互印证，可视为已发生的事实。

### 2.2 核心痛点：N×M 集成难题

假设有 N 个 AI 客户端应用和 M 个外部工具/数据源，缺乏统一标准时，开发者需构建和维护 N×M 个独立连接器，每个都要处理特定认证机制、请求格式、错误处理和数据转换，工作量呈二次方增长，随生态扩张迅速不可持续 [8][12]。MCP 通过建立统一中间协议层，使 AI 应用只需实现一次 MCP Client、工具方只需实现一次 MCP Server，整合数量从 N×M 降为 **N+M** [9][10][11][12]。

### 2.3 次要痛点：供应商锁定与上下文碎片化

- **供应商锁定与低复用**：各 LLM 提供商（OpenAI、Anthropic、Google、Mistral）提供各自不同的 Function Calling/Tools API，为某一模型构建的连接器换到另一模型需重新完整集成；Function Calling 还存在平台锁定、无状态性、缺乏工具发现机制三项结构性限制 [8][12]。
- **上下文接入碎片化**：MCP 之前业内没有通用标准来集成 AI 模型与外部数据及服务，每次集成都定制化且不能互用；LLM 本身知识停留在训练时点、缺乏与外界交互能力，无法访问实时数据或执行动作 [9][10][12]。

MCP 因此被比喻为 AI 应用的"USB-C"通用连接器——安全、标准化、双向、厂商中立且开源开放 [9][10][11][12]。

## 三、生态现状（截至 2026 年）

### 3.1 规范版本演进：两份时间线需辨析

笔记中存在两份不完全一致的版本时间线：

- **来源 [2][7]**：2024-11-05（初始稳定版）→ 2025-03-26 → 2025-06-18 → 2025-11-25（最新稳定版）。
- **来源 [8][21][22][23]**：2024-11-25 发布并开源 → 2025-03-26 引入 Streamable HTTP + OAuth 2.1 → 2025-11-25 重大更新（async tasks、extensions）→ 2026-01-26 发布 MCP Apps → 2026-03-26 Auth 认证转正式、HTTP transport 升级 → 2026-07-28 史上最大修订（协议从有状态改为无状态，取消初始化握手与 Session ID，引入 MRTR，MCP Apps/Tasks/企业级鉴权纳入统一扩展框架，Roots/Sampling/Logging 弃用但保留至少 12 个月迁移期）。

**差异分析**：两份时间线在 2025-03-26 与 2025-11-25 两个节点上一致，分歧主要在起点（11-05 vs 11-25）与 2026 年后续版本。可能的口径原因是：2024-11-05 是规范文档的版本日期，而 2024-11-25 是公开发布/开源日期；2026 年各版本则可能因来源 [2][7] 的页面更新滞后而未收录。**本报告采信 [8][21][22][23] 的完整时间线**，因其覆盖至 2026 年且与其他生态数据（如 SDK 同步情况）相互印证；同时保留 [2][7] 的 2024-11-05 作为规范文档初始版本日期。

### 3.2 SDK 覆盖与下载规模

**语言覆盖**：Tier 1 为 TypeScript、Python、Go、C#（另有 Java SDK 与 Spring AI 集成），Rust SDK 处于 Beta；四大 Tier 1 SDK 已全面同步支持 2026-07-28 规范，社区 SDK 还包括 Swift 等 [8][21]。

**下载规模——数字差异显著，需谨慎采信**：

| 来源 | 口径 | 数字 |
|---|---|---|
| [3] | 较早数据 | 月下载量突破 9700 万次 |
| [20][21][22] | 截至 2026 年 7 月 | 月度 SDK 下载量突破 4 亿 |
| [24] | Tier 1 SDK | 月下载量逼近 5 亿；TypeScript 与 Python SDK 累计下载量均超 10 亿 |

**差异分析**：9700 万与 4–5 亿之间相差约 4–5 倍，最可能的原因是统计时点不同（[3] 为较早数据，[20][21][22][24] 为 2026 年 7 月前后）以及统计口径不同（"全部 SDK" vs "Tier 1 SDK"，"月下载" vs "累计下载"）。**本报告采信"截至 2026 年 7 月，Tier 1 SDK 月下载量约 4–5 亿、TypeScript 与 Python 累计均超 10 亿"**，理由是多个独立来源在相近时点给出一致量级，且与 2026-07-28 大版本发布带来的下载高峰相符；9700 万应视为更早期的历史数据。

### 3.3 客户端接入

Claude Desktop、ChatGPT、VS Code、Cursor、Windsurf、Claude Code 等主流 AI 应用均已支持 MCP；2025 年 5 月出现 IDE 支持浪潮（Cursor、Windsurf、VS Code、JetBrains）；Microsoft 将 MCP 做进 Win11 系统层，阿里云百炼上线全生命周期 MCP 服务 [3][8][23]。

### 3.4 服务器/连接器规模

- 公开注册的 MCP Server **超过一万个**，涵盖数据库、版本控制、通信工具、云服务等 [3][20][22]。
- Claude 连接器目录已收录 **950+ 服务器**，每天被数百万用户使用 [3][20][22]。
- 自 2025 年 5 月以来远程 MCP Server 数量增长近 **4 倍**，80% 热门 MCP Server 提供远程部署支持 [3][20][22]。
- 另有资料口径明显较小，称官方与社区服务器合计"上百个" [3]。

**差异分析**："上万"与"上百"的差距可能源于统计范围不同——前者可能统计所有公开注册/社区收录的服务器（含个人发布），后者可能仅统计官方认证或精选目录。**本报告采信"公开注册服务器超过一万个、Claude 官方目录收录 950+"**，因该数字有多个来源交叉支持且区分了"注册总量"与"官方精选"两个层级。

### 3.5 生态治理与行业采用

- 2025-09 官方 **MCP Registry** 上线 [3][8]。
- 2025-12-09 协议**捐赠给 Linux Foundation** 并成立 AAIF [3][8]。
- 2026-04-02 首届 **MCP Dev Summit NYC** 举办 [3][8]。
- OpenAI 的采用被视为 MCP 从"Anthropic 项目"转为"行业标准"的决定性拐点 [8][32]。
- **Gartner 预测**（预测，非事实）：到 2026 年底 40% 企业应用将包含特定任务 AI Agent（2025 年不到 5%），并预计 75% API 网关厂商、50% iPaaS 厂商将集成 MCP [3][8]。

## 四、与既有方案的差异与互补

### 4.1 MCP vs Function Calling：不同层次，互补而非替代

Function Calling/Tool Calling 是大模型的**推理机制**，解决"模型如何表达意图、输出结构化参数"；MCP 是**应用层通信协议**，解决"AI 应用如何标准化连接外部工具和数据"。MCP 底层仍依赖模型的 Tool Calling 能力，只是做了标准化转换 [14][15]。

集成模式上差异明显：传统 Tool Calling 是每个应用×每个工具的 M×N 紧耦合适配，工具定义硬编码、修改需重新部署；MCP 是 M+N 即插即用，工具定义由 Server 在运行时动态发现，支持热更新、资源绑定、Prompt 模板关联与 annotations，传输统一为 JSON-RPC 2.0 [15][18]。有资料因此把 MCP 概括为"将 Function Calling 进行了标准化" [14]。

### 4.2 MCP vs A2A：工具通讯 vs Agent 通讯

MCP 主攻"Agent 与工具/资源通讯"，A2A 专注"Agent 与 Agent 通讯"，Google 明确表示 A2A 是对 MCP 的补充 [13][16]。用一句话区分：MCP 回答"我的 agent 能用什么工具"，A2A 处理"我的多个 agent 如何协作" [13]。

边界存在模糊与竞争风险：Agent 与 Tool 的界限正在变模糊（如翻译 Agent 从另一 Agent 视角看就是一个工具，OpenAI 的 Agent as tools），有观点认为可能出现 A2A vs MCP 的生态拉锯；短期内两协议平行发展，实践中可在智能体密集互动场景用 A2A、模型调外部资源场景用 MCP [13]。

### 4.3 MCP vs RAG

RAG 不是 agent 必须遵循的协议，而是一种改善底层 LLM 输出的方法；RAG 常与 A2A、MCP 重叠，agent 可以把 MCP server 的工具调用作为 RAG 流水线中的一步来检索数据 [17]。

### 4.4 资料缺口

**OpenAI Plugins 与 LangChain Tools 的具体定位与能力边界，笔记中未涉及**，本报告不对其作比较性论断。

## 五、落地中的主要问题与争议

### 5.1 安全与权限

MCP 不替代所连服务的安全控制，安全性取决于客户端、服务器、身份、令牌、范围、权限、可用工具与源内容的整条链路；最常见风险包括权限过多与上下文过度共享、不受信任或被入侵的服务器、不安全或破坏性操作、审批控制薄弱、令牌/会话/审计漏洞 [27]。

### 5.2 供应链与命令执行风险

MCP 服务器由可执行代码组成，存在依赖篡改、恶意更新、命令注入等风险。应对措施包括：仅使用可信服务器、组件签名、SAST/SCA 管道、加密服务器验证、依赖完整性与恶意软件扫描，以及在沙盒中运行本地服务器 [25]。

### 5.3 提示注入与工具投毒

恶意指令可隐藏在文件、网页、工具描述、函数名、参数或错误信息中，诱导 AI 执行用户未打算的操作。业界建议将检索内容与工具元数据视为不受信任、验证工具定义、限制可用工具、不靠文档授权操作，并实时分析可疑提示、记录审计日志 [25][27][30]。安全研究显示**工具中毒攻击成功率最高达 72.8%**，深度防御与标准化安全审计是当务之急 [8]。

### 5.4 认证授权

MCP 采用 OAuth 定义授权机制，但现行规范部分实现细节与现代企业实践冲突，业界正积极完善更新授权规范；身份管理与策略执行仍是关键空白，缺乏身份建模与策略编排导致工程师不愿采用完全集中式 MCP 结构，产生运营摩擦与安全债务 [25][26]。

### 5.5 官方与生态的应对

- **OWASP MCP Azure 安全指南**列出十大风险（令牌管理不善、权限蔓延、工具中毒、供应链攻击、命令注入、意图流篡改、认证授权不足、审计遥测缺失、影子 MCP 服务器、上下文注入与过度共享）并给出对应缓解措施 [31]。
- MCP 规范在认证上已从自定义认证服务器演进为**可委托外部身份提供者**（如 Microsoft Entra ID），并增强 STDIO 与 Streamable HTTP 的传输层安全 [31]。

### 5.6 企业部署与运维成本

MCP 协议设计上未太多考虑企业级落地，导致许多企业处于观望；落地面临认证鉴权受限、部署模式多样、技术债务风险等挑战。应对路径包括建设中心化注册中心、可控软件供应链与安全访问控制（如以 Nacos 作注册中心与路由、配合 Higress 做安全访问），并按数据敏感度、延迟、可扩展性选择本地/云端/混合架构 [28][29]。

## 六、未来演进与竞争格局

### 6.1 官方路线图（预测性内容）

2026 年 3 月发布的 MCP 官方路线图明确四大优先领域：**传输层可扩展性、Agent 通信、治理成熟、企业就绪**；下一规范版本预计 2026 年 6 月发布 [8]。需注意，截至本报告日期（2026-11-04），该"预计 6 月发布"的版本在笔记中未见后续确认，实际最新规范为 2026-07-28 的大修订 [21][22]，两者关系笔记未明确说明。

### 6.2 传输层：从有状态走向无状态

Streamable HTTP 在大规模运行中暴露有状态会话与负载均衡器冲突、水平扩展需粘性会话等问题，工作组正推进会话恢复协议、无状态服务器架构（外部会话存储）和 .well-known 元数据格式三项修复 [8]。2026-07-28 规范已将协议从有状态改为无状态（取消初始化握手与 Session ID），可视为这一方向的实际落地 [21][22]。

### 6.3 Agent 通信与治理

MCP 服务器将从单纯工具提供者扩展为能接收任务、评估策略、协商范围、委托子工作的自主参与者，使 MCP 从工具调用协议演化为更完整的 Agent 协作协议 [8]。治理上，AAIF 正为规范各领域建立标准化工作组，引入社区驱动提案流程、合规性测试和正式审查，目标是使 MCP 演进不再依赖 Anthropic 内部路线图 [8]。

### 6.4 企业级能力差距

MCP 在审计日志、SSO 集成、细粒度访问控制等方面仍需追赶传统企业集成标准 [8]。

### 6.5 竞争格局

MCP 与 A2A 被判断为互补而非竞争，但实际无缝集成及与 ACP（已并入 A2A）遗留系统的兼容仍需更多实践与标准化；未来**可能出现**统一 Agent Gateway 自动适配、路由、转换三大协议（此为业界观点/预测）[8][35]。落地路径建议：先建 MCP 网关统一 AI 访问内部资源入口（ROI 最高起点），再边缘部署 ACP、对外能力 A2A 化，最终构建云-边-端一体化平台 [35]。

## 结论与建议

**核心结论**

1. **MCP 的本质是"AI 应用层的 USB-C"**：它不替代模型的 Function Calling 能力，而是在应用层把 N×M 的定制集成降为 N+M 的标准适配，这是其被快速采纳的根本原因 [8][12][15]。
2. **生态已跨过"事实标准"门槛**：规范多轮大改、四大 Tier 1 SDK 同步、主流客户端全面接入、注册服务器过万、协议捐赠 Linux Foundation，均表明 MCP 已不再是单一厂商项目 [8][21][22][23]。
3. **安全与企业就绪是最大短板**：工具中毒攻击成功率最高达 72.8%，认证授权规范与企业级审计/SSO/细粒度访问控制仍在追赶，这是企业观望的主因 [8][25][27][31]。

**按场景的选择建议**

| 场景 | 建议 |
|---|---|
| **个人开发者/小团队快速接入外部工具** | 直接采用 Tier 1 SDK（TypeScript/Python）构建 MCP Server，优先使用 STDIO 本地传输，复用官方 Registry 中的现成连接器 [8][21] |
| **需要模型表达结构化调用意图** | 保留 Function Calling 作为模型侧机制，用 MCP 做标准化封装，二者叠加而非二选一 [14][15] |
| **多 Agent 协作场景** | Agent 与工具通讯用 MCP，Agent 与 Agent 协作用 A2A，二者平行部署 [13][16] |
| **企业规模化落地** | 先建 MCP 网关作为统一入口（ROI 最高起点），配套中心化注册中心（如 Nacos）与安全访问控制（如 Higress），按数据敏感度选择本地/云端/混合架构；同步落实 OWASP 十大风险缓解措施与沙盒隔离 [28][29][31][35] |
| **对安全敏感的生产环境** | 仅使用可信服务器、启用组件签名与 SAST/SCA 管道、将工具元数据视为不可信、限制可用工具集、开启审计日志 [25][27][30] |

**待观察事项**：2026-07-28 无状态化大改的迁移进度（Roots/Sampling/Logging 有至少 12 个月迁移期）、官方路线图中"2026 年 6 月下一版本"与实际 7 月大修的关系、以及 MCP 与 A2A 是否会走向统一 Agent Gateway [8][21][22][35]。
