# LangGraph、CrewAI、AutoGen 多智能体框架选型研究报告

## 摘要

本报告基于现有研究笔记，对 LangGraph、CrewAI、AutoGen 三个多智能体框架的定位、核心抽象、版本演进、状态管理与可观测性等维度进行梳理。总体来看，三者在设计理念上形成清晰分野：LangGraph 以「图」为核心抽象，强调状态机式编排与流程掌控力，生产验证最充分 [1][2][5]；CrewAI 以「角色」为核心抽象，通过 Role/Goal/Tools 的角色化分工模拟团队协作 [1][2][4]；AutoGen 以「对话」为核心抽象，依靠自然语言协商实现灵活协作，但已进入维护模式，新项目建议转向 Microsoft Agent Framework [1][3][5][6]。需要说明的是，笔记中关于性能、成本、学习曲线的实测数据以及部分横向对比内容存在缺失或对象界定不清的问题，本报告对无法支撑的结论将如实标注。面向未来，MCP/A2A 协议分层与平台化托管将深刻影响选型逻辑，框架选择需与协议契约、平台能力一并考量 [22][23][26]。

---

## 一、三个框架的定位、设计理念与核心抽象

### 1.1 LangGraph：以「图」为核心的状态机编排框架

LangGraph 定位为图式编排/状态机框架，是 LangChain 生态的重要组成部分，专注状态图多 Agent 编排，生产验证最为充分 [1][2][5]。其设计理念以状态机为核心，将工作流表示为节点（计算单元，可为 Agent 或工具）与边（流程走向），支持高度模块化、条件分支、循环与持久化 [1][2][5]。

其核心抽象是「图」：节点与边构成状态图，配合基于状态的记忆与检查点机制保证工作流连续性，并可强制执行严格输出格式与状态转移 [1][2]。代价是需要更深入理解图设计，学习曲线较陡，但换来更强的流程掌控力 [1][2]。

### 1.2 CrewAI：以「角色」为核心的角色化协作框架

CrewAI 定位为角色化多 Agent 协作框架（开源、Python、宣称独立轻量），设计理念是「角色化协作」——把复杂任务分解，为每个 Agent 分配角色（Role）、目标（Goal）和工具（Tools），像管理一个团队一样在结构化流程（Process）中接力完成任务 [1][2][4]。

其核心抽象是「角色」三件套：Agent（定义角色和工具）、Task（具体工作单元与期望输出）、Crew（编排 Agent 与执行流程）；Process 有 sequential（顺序）和 hierarchical（层级，由 Manager Agent 协调）两种模式 [2][3]。该框架属 Role-Based 预定义分配，易预测但灵活性较低 [2][3]。

### 1.3 AutoGen：以「对话」为核心的对话式协作框架

AutoGen 定位为微软研究院开源的多智能体对话协作框架（支持 Python 和 .NET，异步事件驱动架构），设计理念是「对话式协作」——Agent 通过自然语言对话协商完成任务而非被预先编程好行为，强调灵活性与可扩展性，适合研究与复杂问题探索 [2][3][4]。

其核心抽象是「对话」：采用群聊/群组管理器模型，Agent 之间及人与 Agent 之间以自然语言对话、讨论甚至辩论协作，属对话涌现的自主协商，更灵活但更难调试、可预测性较低 [1][3]。资料另指出 AutoGen 已进入维护模式，新项目建议改用 Microsoft Agent Framework [1][3][5][6]。

## 二、版本演进、维护活跃度与社区生态

### 2.1 版本与发布节奏

- **LangGraph**：1.0 于 2025-10-24 GA（LangChain 1.0 于 2025-10-23 GA），核心新抽象为 `create_agent`，已废弃 `create_react_agent`；LangGraph 专注状态图多 Agent 编排，生产验证最充分 [5]。
- **AutoGen**：已进入维护模式，仅提供安全补丁与关键修复，不再有新功能；README 明确说明不再接收新功能/增强、转为社区管理，新用户应改用 Microsoft Agent Framework；社区分支 AG2 继续独立演进 [5][30][32][35]。其最后一个标记版本为 python-v0.7.5（2025-09-30 发布，PyPI 上 autogen-agentchat 0.7.5 同日上传），此后长期无新版本发布（有资料称约 320 天/十个半月无 release）[30][32]。
- **CrewAI**：2025 年的具体版本号未明确给出，仅提及 0.95 增加工具调用路由改进与实验性异步 crew runner，以及 1.15.28 为 2026-10-14 的版本 [31][32]。

三个框架的贡献者数量在所有资料中均未提及 [5][30][31][32]。

### 2.2 GitHub Star 与生态

GitHub star 数据各资料口径不一：AutoGen 约 60,400（另有 60,475、约 42,000 的说法），CrewAI 约 57,100–57,217（另有 50.8k、30K+ 的说法），LangGraph 约 39,800–39,876；资料指出 star 数反映历史积累，不代表当前活跃度 [29][30][31][33][35]。

从使用率看，LangChain 以 55.6% 的开发者使用率占据 AI Agent 框架核心地位（据 Upwork 542 个项目统计，2025）；AutoGen（Microsoft）以 21.2k GitHub Stars 稳居多智能体对话框架前列，核心特色为多轮对话优化与人类反馈机制；CrewAI 以「Agent 如同微服务团队」的设计理念开辟差异化路线 [8]。需注意，该资料未给出 CrewAI 的 star 数或发布数据 [8]。

### 2.3 Microsoft Agent Framework 与 AutoGen 的关系

Microsoft Agent Framework 是微软统一 Agent 框架，已统一 AutoGen + Semantic Kernel 的多 Agent 模式，支持 Python 和 .NET；2025-10 公开预览 → 2026-02-19 RC → 2026-04-02 发布 1.0 GA，13.7K star，被定位为 AutoGen 的企业级继任者并承诺长期支持（LTS）[5][29]。

## 三、编排模型、状态管理与人机协同差异

### 3.1 状态管理（检查点/持久化）

- **LangGraph**：采用集中、显式的状态贯穿节点，内建 Checkpointer 支持持久化/检查点（如存储聊天记录），支持局部重试与补偿机制；相比之下，LangChain 的状态管理通常是隐式或组件本地的；LangSmith 本身不是执行框架，只存储运行的元数据、输入/输出、指标与反馈，无控制流能力 [37][41]。
- **AutoGen**：通过对话历史自动管理状态（AgentSession 管理聊天状态），但相比 Microsoft Agent Framework 的检查点，AutoGen 缺少自动持久性、精细恢复、状态隔离与容错等能力；Agent Framework 检查点可从任何超级步骤边界恢复并支持子工作流检查点 [39][40]。

### 3.2 人机协同（Human-in-the-loop）

- **LangGraph**：原生支持在特定节点设置断点，暂停执行等待人类审核确认后再继续，对敏感操作尤为关键 [39]。
- **CrewAI**：仅有限支持 [39]。
- **AutoGen**：通过 `human_input_mode` 参数支持人机协同 [39]；Microsoft Agent Framework 则提供 Request-Response API 与带人工审批入口的持久化工作流，实现无缝暂停恢复，检查点式的人机循环集成是 Agent Framework 的增强项 [40]。

在人机协同的概念层面，资料区分了多种控制模型：HITL（人类在任何操作发生前主动审核任务）、HOTL（人类监控系统但不必批准每个决策，模型保留一定自主权）、HIC（人类完全掌控系统并可随时关闭），以及 human-out-of-the-loop（人预先设定规则、事后审计）[9][10]。HITL 与 HOTL 的核心差异在于时机与吞吐：在环监督发生在行动之前，系统规模随审核者数量扩展；在环上监督发生在行动之中或之后，系统规模随系统自身容量扩展，监督成本随业务量增长更慢 [9]。HITL 的实现依赖置信阈值与升级逻辑，人类更正会回流用于模型再训练 [10]；其主要权衡是准确性提升与可扩展性下降 [12]。

### 3.3 可观测性与调试工具

- **LangSmith**：专门的追踪/评估/监控平台，支持语言无关的追踪（Python、JavaScript、REST API）、运行回放、提示管理与并排比较，灵活性评分 9/10，但自主智能体追踪并非其专精（7/10）[36][38]。
- **AgentOps**：专为自主智能体监控打造（自主性 9/10），专注追踪复杂思维链与多步决策，但功能广度较窄（灵活性 6/10）[36][38]。
- **AutoGen**：内置监控能力极少，需额外定制方案，可观测性仅属中等（对话日志），但原生支持 OpenTelemetry（运行时跟踪、工具执行、代理操作跨度）[36][39][40]。
- **LangGraph**：可观测性优秀，与 LangSmith 深度整合 [36][39][40]。

资料中未提及 AutoGen Studio 的具体能力 [36][39][40]。

> **说明**：笔记中关于「三者在编排模型、状态管理、可观测性与调试能力上的横向对比」部分资料并未明确界定「三者」的具体指代对象，也未提供完整的横向对比内容，本节仅就各框架可提取的具体能力进行归纳 [9][10][12]。

## 四、多智能体协作模式与工具/记忆/模型接入

### 4.1 协作模式谱系

资料列举了顺序交接、并行处理、辩论与共识、层级结构、专家团队、评审者模式，以及网络化、监督者模式、监督者作为工具、自定义架构等协作模式 [14][15]。层级与群聊的差异在于：层级模式由 Manager Agent 分配任务给 Worker Agent，CrewAI 通常借助 LLM 与上下文自动判断，AutoGen 则支持随机、顺序、自动、自定义等决策模式；群聊方面 AutoGen 使用 GroupChat 机制支持多 Agent 轮流对话 [15][16][18]。

角色可划分为 Planner、Researcher、Executor、Evaluator，每个 Agent 可具备专属能力、记忆、目标和行为策略；并行工作流需状态管理、任务队列、权限、可观测性与验证，图工作流支持基于 DAG 的分支汇合 [15][16][18][20]。

### 4.2 工具与记忆接入

单智能体可通过函数调用访问外部 API、数据库、文件、网页抓取与搜索，并具备短期对话历史加向量数据库支撑的长期记忆与上下文窗口管理；多智能体层面每个 Agent 可拥有自己的「工具箱」并通过插件机制调用工具，记忆分为私有记忆与共享记忆，通信可采用共享内存/黑板机制、数据库/RAG 存储共享信息 [15][18][20]。

### 4.3 模型接入

Agent 可以是独立的大模型实例，也可以是微调后的轻量模型，甚至规则引擎或工具包；单智能体支持多模态输入、流式输出，并能在主模型失败时自动切换到备用模型；IBM Bee 框架支持 IBM Granite、gpt-4 和 Llama 等模型 [15][17][18]。

> **说明**：该子问题的资料未明确界定「三者」具体所指，也未提供针对三个特定系统的横向对比，本节仅从各资料中分别提取不同框架/系统的协作模式与接入特征 [14][15][16][17][18][19][20]。

## 五、性能、成本、学习曲线与生产案例

### 5.1 数据可得性说明

笔记中未提供任何关于三者性能、成本、学习曲线或生产案例/社区反馈的具体信息，也未明确界定「三者」具体指哪三种技术/方案，因此无法确定性地把数据对应到三个对象上 [42][43][44]。以下仅列出资料中可引用的实测数据与案例，供参考。

### 5.2 延迟相关实测

MeshFusion（XSKY）在华为昇腾910C上处理128K上下文时，SSD卸载使单卡可服务并发数从2提升至8（4×），每Token延迟从1.2s增至1.8s（增幅50%）；三层存储访问延迟分别约0.1μs（GPU HBM）、0.1ms（CPU DRAM）、0.1s（SSD），智能预取将SSD访问延迟对用户影响控制在5%以内 [42]。

### 5.3 Token 成本相关数据

InferenceX 的 GB200/GB300 对照（固定 V4-Pro、FP4、输入8192/输出1024，Dynamo+vLLM PD分离，无推测解码，测量日期2026-05-22）在约27 token/s/user处列出6182对2189 token/s/GPU，采用$2.65对$2.21/GPU-hour的TCO假设，吞吐比约2.82、成本比约2.36（正文另报2.31，无法由取整值精确复现，报告保留「约2.3倍」量级）；NVIDIA 2026年文章引用Blackwell Ultra对Hopper在低延迟区间最多35倍的token成本差异，且软件优化参与其中 [43]。

压缩与预填充成本方面：OSCAR 2-bit KV Cache量化相比BF16将KV Cache内存降低约8倍，8×压缩下PPL增加<0.5；ParaCache约节省30%-50%预填充时间；Gisting训练实现高达26×提示词压缩（如2048 Token压缩至80 Gist Token）；AGORA实现11.5×压缩比；EHPC在LongBench上50% Token丢弃率下性能损失<3% [42]。

### 5.4 企业落地与社区反馈

FlexKV（腾讯）已合入NVIDIA Dynamo、vLLM、TensorRT-LLM三大主流推理框架官方主线；MeshFusion完成DeepSeek V4、GLM-5.2、Qwen3.5/3.6等国产模型验证；九章云极尚明栋团队实测仅缓存机制一项即可避免至少10%的重复计算，通义千问3.5等新模型已在架构层面自带KV Cache压缩机制；云器科技通过内部可观测系统追踪各模型调用成功率、Token消耗、Tool Calling能力 [42][44]。

学习曲线方面，资料中未提供任何关于三者学习曲线的实测数据或案例，仅有关于使用习惯的定性建议（如保持上下文围绕同一任务以提升缓存命中率、避免过度堆积历史导致Token浪费与缓存失效），不足以支撑学习曲线的量化比较 [44]。

## 六、未来 1-2 年演进趋势对选型的影响

### 6.1 协议分层而非二选一

生产实践正在形成分层架构——工具层用 MCP、协调层用 A2A、接口边界把协议当作契约规范而非实现框架，内部智能体代码可用任何最有能力的框架，协议只是可移植的翻译层 [22][23][27]。

### 6.2 MCP 的规模优势与 A2A 的引入门槛

到 2026 年初，每个主要 AI 提供商（Anthropic、OpenAI、Google、Microsoft、Amazon）都采用 MCP，Claude 目录有 75+ 官方连接器，通常可从现成代码起步；MCP 适合对可靠性、隐私、合规要求高的企业级场景 [22][23]。A2A 的引入门槛在于：只有当至少有两个需协作的独立智能体、尤其跨组织或框架边界时才引入 A2A；在单智能体或紧耦合多智能体场景中，Agent Card 带来的发现复杂性是真实开销 [22]。

### 6.3 碎片化风险与治理信号

协议碎片化风险正转向实现层：规范稳定但实现不一致（MCP 子集、错误处理、能力协商差异），这是 2026 年多数实际协议痛点；同时 AG-UI 这类人机同步层尚无稳定标准，是可能出现新规范工作的领域 [22]。2025 年 12 月 Agentic AI Foundation（AAIF）在 Linux 基金会下成立，由 Anthropic、OpenAI、Block 共同创立，Google、Microsoft、AWS、Cloudflare、Bloomberg 为铂金会员，表明协议碎片化问题正被机构化应对 [22]。

### 6.4 框架与平台层同步成熟

LangChain/LangGraph、AutoGen、CrewAI 等开源框架繁荣，Dify、FastGPT、Coze 等低代码平台降低门槛；MCP 与 A2A 被视为 Agent 互联网的底层通信基础设施，选型需同时考虑框架与平台托管能力 [26]。

## 七、选型建议小结

综合笔记信息，可形成如下初步判断：

1. **追求流程掌控与生产稳定性**：LangGraph 以图式状态机编排、内建 Checkpointer、原生 HITL 断点与 LangSmith 深度整合见长，生产验证最充分，适合对流程可控性、状态持久化与可观测性要求高的场景 [1][2][5][37][39]。
2. **追求快速搭建角色化团队协作**：CrewAI 的 Role/Goal/Tools 三件套与 sequential/hierarchical 两种 Process 模式上手直观、易预测，适合任务可分解为明确角色的协作场景，但灵活性较低、HITL 支持有限 [1][2][3][39]。
3. **新项目应审慎选择 AutoGen**：AutoGen 已进入维护模式，仅安全补丁与关键修复，新用户应改用 Microsoft Agent Framework；若需延续 AutoGen 路线，可关注社区分支 AG2 或迁移至 MAF（已统一 AutoGen + Semantic Kernel 多 Agent 模式并承诺 LTS）[5][29][30][32][35]。
4. **面向未来的协议与平台考量**：选型时应将 MCP（工具层）与 A2A（协调层）视为契约规范而非实现框架，内部实现可自由选择框架；同时评估平台托管能力与协议实现一致性风险 [22][23][26]。

> **局限说明**：本报告在性能、成本、学习曲线的量化对比以及部分横向对比维度上受限于笔记资料缺失，相关结论仅为定性判断，实际选型建议结合 PoC 实测补充验证。
