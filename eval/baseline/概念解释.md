# MCP（Model Context Protocol）协议研究报告

## 摘要

MCP（Model Context Protocol，模型上下文协议）是由 Anthropic 于 2024 年底发布的开放标准协议，基于 JSON-RPC 2.0 构建，旨在实现 AI 应用与外部数据源、工具之间的标准化连接[1][2][3][4][7]。它采用 Host-Client-Server 架构，通过 Tools、Resources、Prompts 三种核心原语暴露能力，并定义了 stdio 与 Streamable HTTP 两种标准传输方式[1][5][6]。MCP 主要解决 LLM 应用接入外部工具时的 M×N 集成爆炸、各厂商函数调用标准割裂、上下文手工构造困难以及权限管理碎片化等痛点，将 N×M 次对接简化为 N+M 次开发[4][9][10][11][12]。在生态层面，MCP 已获得 Claude Desktop、Cursor、VS Code、ChatGPT 桌面版等主流客户端以及 LangChain、Semantic Kernel 等 Agent 框架的支持，公开 MCP Server 数量已达万级规模[20][21][22][24][26]。与此同时，工具投毒、提示注入、权限认证与供应链风险等安全治理问题日益突出，业界正通过规范演进与纵深防御实践加以应对[27][29][30][31]。未来 MCP 将围绕标准化注册中心、多模态、行业化以及与 A2A 等协议的协作融合持续演进，但仍面临安全、企业级功能与路线之争等不确定性[13][22][36][38][39]。

## 一、MCP 协议的定义、核心架构与传输方式

### 1.1 协议定位与提出者

MCP（Model Context Protocol，模型上下文协议）是由 Anthropic 于 2024 年 11 月（2024 年底）发布的开放标准协议，基于 JSON-RPC 2.0 构建，用于实现 AI 应用程序与外部数据源、工具之间的标准化连接[1][2][3][4][7]。

### 1.2 核心架构：Host-Client-Server

MCP 采用客户端-宿主-服务器（Host-Client-Server）架构：Host 是包含 LLM 的 AI 应用/环境（如 AI 辅助 IDE、对话式 AI），是用户交互点；Client 负责连接 MCP Server；Server 暴露能力。协议遵循"服务端应极其易于构建"原则，将安全策略、用户授权、上下文聚合等编排职责交给宿主应用[1][4][6]。

### 1.3 三种核心原语

MCP 通过三种核心原语暴露能力：Tools（工具，适合可执行动作）、Resources（资源，适合被读取的上下文资料，如数据库、API、第三方 SaaS）、Prompts（提示词，适合可复用提示模板），使 AI 模型能够动态发现并调用外部能力[1][5][6]。

### 1.4 传输方式

- **Stdio 传输**：使用标准输入/输出流进行同一机器上本地进程间的直接通信，无需网络开销、性能最佳，通常只服务单个 MCP 客户端，适用于本地文件、本地数据库等场景[1][6]。
- **Streamable HTTP 传输**：使用 HTTP POST 发送客户端到服务端的请求，并结合可选的服务器发送事件（SSE）实现流式功能，支持远程服务器通信及标准 HTTP 认证（Bearer 令牌、API 密钥、自定义标头），MCP 建议使用 OAuth 获取身份验证令牌[1]。
- **规范演进**：在 2025 年 3 月 26 日的规范修订中，早期的 HTTP+SSE 传输机制被标记为已弃用，新开发的服务端应统一使用 Streamable HTTP 传输；当前规范重点为标准传输 stdio 与 Streamable HTTP[1][6]。

## 二、MCP 解决的痛点与核心价值

### 2.1 MCP 出现前的行业痛点

- **M×N 集成爆炸**：MCP 推出前，将 LLM 连到各种外部数据源和工具通常必须采用特殊连线或各供应商专属方法，导致系统杂乱，即所谓「N x M」问题——每新增一个模型或工具，所需的自定义连接数量就迅速增加[4]。
- **集成呈"烟囱式开发"**：每个模型需单独对接不同数据源，导致开发成本高、安全性差、扩展困难；且缺少一个开放的、通用的、有共识的协议标准[12]。
- **各厂商函数调用标准割裂**：function call 平台依赖性强，不同 LLM 平台的 API 实现差异较大（如 OpenAI 与 Google 不兼容），开发者切换模型时需重写代码，增加适配成本，此外还有安全性、交互性等问题[9]。
- **手工构造上下文困难**：没有 MCP 之前，人们往往人工从数据库筛选或用工具检索信息再手动粘贴进 prompt，随着问题变复杂，手工把信息引入 prompt 越来越困难[9]。
- **权限管理碎片化与跨系统集成复杂**：以某银行传统 RAG 方案为例，不同部门知识库权限规则不同且需与检索逻辑绑定，易出现权限漏洞；结合客户数据时需单独开发 CRM 与合规库对接接口，重复劳动多；新增知识源需重构 LLM 调用逻辑，开发周期长达 2-3 周[10]。

### 2.2 MCP 的解决方式

- **通用开放标准简化连接**：MCP 提供通用开放标准（如 USB-C），降低开发成本、加快 AI 应用构建，开发者可轻松切换不同供应商的 LLM 及新增工具而无需重大变更；将过去 N 个模型、M 个服务对接需 N×M 次开发简化为 N+M 次开发[4][11]。
- **解耦与权限独立部署**：通过标准化工具定义和协议接口，LLM 无需关心底层存储与检索细节；新增知识源或集成新系统只需开发对应 MCP 工具并注册到服务器，无需修改 LLM 核心逻辑；安全权限、日志审计可独立部署于 MCP 层，与业务逻辑分离[10]。
- **附加能力**：MCP 还带来数据实时流动、本地执行保护隐私、自动工具发现与上下文管理等能力，并减少模型幻觉、提升自动化程度[4][11]。

## 三、MCP 与其他方案的异同与互补关系

### 3.1 MCP 与 Function Calling

MCP 与 Function Calling 是互补而非替代关系：Function Calling 关注如何把 tools 信息告知模型、模型如何判断调用哪个 tool；MCP 则定义 MCP Server 如何对外暴露能力、他人如何调用 MCP Server，可理解为 MCP 将 Function Calling 进行了标准化[15][17][18]。

Function Calling 缺乏统一标准，不同模型（GPT/Claude/DeepSeek）调用规则不同，M 个模型应用对接 N 个工具理论上需 M×N 次重复对接；MCP 通过统一接口标准把 M×N 问题转化为 M+N 问题，工具方只需实现一次 MCP Server，应用方只需实现一次 MCP Client[16][17]。此外，Function Calling 本身不直接支持函数链式调用，模型一次只能调用一个函数，需应用层编排把前一函数结果输入下一轮对话；MCP 通过统一接口标准解决该问题，并引入客户端-服务器架构（Host/Client/Server），具备更清晰的职责划分与扩展性[16][17]。

### 3.2 MCP 与 A2A

MCP 与 A2A 是互补关系、面向不同维度：MCP 是 Agent 向下连接工具和数据源（纵向），A2A 是多个 Agent 之间横向通信协作、委派任务、接收结果，一纵一横各管一层，不存在谁替代谁；复杂多 Agent 系统中通常两者同时使用[14][16]。

从阵营看，A2A 由 Google 主导并于 2025 年 4 月开源，发布即结盟 50 多家合作伙伴（Atlassian、Salesforce、SAP、Cohere、LangChain 等），但 OpenAI/Microsoft 阵营缺席；MCP 由 Anthropic 倡议，获 Google Cloud、AWS 支援，微软在 Copilot X 中整合 MCP，阿里、腾讯等也迅速介入[13]。

关于 MCP 与 A2A 的边界存在争议：有观点认为 Agent 与 Tool 界限正变模糊（如翻译 Agent 从另一 Agent 视角看就是工具），开发者精力有限可能只选其一，Solomon Hykes 预见会出现 A2A vs MCP 的拉锯；也有观点提出可设计统一代理通讯层，同时涵盖 Agent-Agent 对话与 Agent-Tool 呼叫[13]。

### 3.3 MCP 与 LangChain Tools

LangChain Tools 与 MCP 可混合使用：可用 LangChain 的 function-calling 对接 OpenAI 或 Anthropic 工具，用 MCP 处理其余部分，二者不冲突；MCP 工具可运行在不同服务器、容器甚至不同语言上，LangChain agent 无需了解其内部实现，但存在 schema 不匹配、远程调用延迟等挑战[19]。

## 四、MCP 生态现状

### 4.1 SDK 与多语言支持

MCP 发布时即开源 Python/TS SDK；Python 的 FastMCP 框架最为成熟，TypeScript/JavaScript 适合 Web 开发者，.NET 由 Microsoft 提供官方模板和 NuGet 包，Go/Java 为社区维护的 SDK。官方 SDK 支持最好，否则建议使用 Python[21][22][25]。

### 4.2 官方与社区开源资源

GitHub 组织 modelcontextprotocol 收录协议规范、SDK 实现、示例服务器；官方维护的参考服务器集合包含文件系统、GitHub、Google Drive、PostgreSQL 等集成；官方还提供可视化调试工具 inspector。社区侧有 awesome-mcp-servers 汇总列表（数千条目）和 mcp.so 中央目录（聚合超 1.8 万个第三方服务器）[20][26]。

### 4.3 主流客户端支持

Claude Desktop 是 MCP 的原生参考实现并开放插件接口；Cursor 深度集成 MCP；VS Code 通过 GitHub Copilot Chat 扩展支持；Windsurf 提供策划的 MCP 服务器目录；Zed 内置 MCP 客户端；JetBrains IDEs 在 2025 年发布中引入支持；ChatGPT 桌面版于 2025 年 3 月全面集成；Gemini/Google AI Studio 亦支持[20][21][22]。

### 4.4 Agent 框架与平台支持

Microsoft Copilot 通过 Semantic Kernel 和 Azure OpenAI 集成 MCP，LangChain 已支持；OpenAI 于 2025 年 3 月宣布 Agent SDK 支持 MCP[22][24]。

### 4.5 公开 MCP Server 数量

不同来源数据不一——有称公开注册的 MCP Server 超过万个，mcp.so 聚合超 1.8 万个，另有资料称接近 5000 个；SDK 月下载量约 9700 万次；自 2025 年 5 月以来远程 MCP Server 数量增长近 4 倍，80% 热门 Server 提供远程部署支持[21][24][26]。

### 4.6 典型应用场景

典型场景包括：企业智能化（数据分析、知识管理、业务决策，金融/医疗连接实时数据）、开发工具（浏览器自动化、UI 创建、视频字幕提取）、自动化日程管理、文档检索、客服机器人数据查询、AI 编辑器与聊天界面、自动化流程等；Server 覆盖数据库、版本控制、通信工具、云服务等领域[20][21][24][26]。

## 五、企业落地中的安全与治理问题

### 5.1 主要安全威胁

- **工具投毒**：是 MCP 最严重威胁之一，攻击者在工具描述/元数据中植入对用户不可见但模型可见的恶意指令（如诱导读取 SSH 私钥并外传），且具有持久性——被投毒的工具描述随包、配置文件或远程服务器分发后，每次调用、每个会话、每个用户都会中招[30][33][34]。
- **间接提示注入与外部数据源风险**：MCP Client 在组装 Server 返回结果时应明确告知 LLM 不对其内容执行任何指令；此外还存在工具冲突、地毯式骗局（工具版本变更后行为改变）等新型风险[31]。
- **权限与认证**：这是 MCP 防御前线，MCP 采用 OAuth 定义授权机制，但现行规范部分实现细节与现代企业实践冲突，业界正积极完善授权规范；企业落地中可用工具往往有权限，而 MCP 在工具权限处理上存在诸多不足[27][28][32]。
- **供应链风险**：MCP 服务器由可执行代码组成，生态无监管生长形成信任匮乏的软件供应链；应对实践包括组件签名、SAST/SCA 管道、依赖完整性验证与恶意软件扫描、加密服务器验证，并将模型、嵌入、上下文提供者、外部 API 等所有 AI 生态组件视同传统软件依赖管理[27][29][33]。

### 5.2 认证规范演进

早期规范要求 MCP 服务器自建 OAuth 2.0 授权服务器直接管理用户身份；当前标准（2025-11-25）允许将认证委托给外部身份提供者（如 Microsoft Entra ID），并增强 STDIO 与 Streamable HTTP 传输层安全机制[29]。

### 5.3 业界应对实践

OWASP MCP Azure 安全指南列出十大风险（令牌管理不善、权限蔓延、工具中毒、供应链攻击、命令注入、意图流篡改、认证授权不足、审计缺失、影子 MCP 服务器、上下文注入与过度共享）并给出缓解措施；微软提出分层安全方法与提示防护、Azure 内容安全、带 PKCE 的 OAuth 2.1、避免令牌透传等最佳实践；火山引擎提出安全准入、原生安全设计与运行时防护；社区强调纵深防御（最小权限+工具 allowlist、网关过滤元数据、运行时监控、人在回路）并把检查自动化到 CI[29][30][31]。

## 六、未来演进方向、争议与不确定性

### 6.1 演进方向

MCP 未来演进围绕标准化、协作化、多模态化、行业化四大方向：建立统一的 MCP Registry（含签名验证与安全认证）形成可信服务器目录；通过采样（Sampling）请求扩展模型间调用实现工具自协作；支持图像、语音、视频等多模态 I/O；在医疗、金融、法律、教育等出现行业级 MCP 服务器与审计规范[36]。

关键发展路线包括官方注册中心、采样功能、跨协议兼容（与 LangChain Tool、OpenAI Function 等标准融合以降低生态割裂）、多模态输入输出、领域化垂直生态；生态集成趋势是成为"跨标准协作层"，使开发者在单一运行时组合异构协议[36]。

### 6.2 与 A2A 的协作与治理融合

MCP 与 A2A 被定位为互补而非竞争：MCP 标准化 Agent 与工具/数据源之间的垂直连接（"白盒"），A2A 标准化 Agent 之间的水平协作（"灰盒"，以 Task 状态机与 Agent Card 发现机制为核心）。2025 年 8 月 IBM 将 ACP 合并入 A2A，2025 年 12 月 A2A 与 MCP 一同加入 AAIF，接受 Linux 基金会治理[22]。

### 6.3 争议与不确定性

- **"A2A vs MCP"路线之争**：有观点认为 Agent 与 Tool 界限正在模糊（如翻译 Agent 可视为工具、OpenAI 的 Agent as tools），开发者可能倾向用一套协议解决；Solomon Hykes 认为理论上可共存但实际会有拉锯，开发者精力有限不会同时投入多个生态，若多数只选其一，另一个可能边缘化。也有人提出设计统一代理通讯层、视情景套用不同子协议，或短期"双标"并存、各取所长[13]。
- **安全挑战**：工具中毒攻击成功率最高 72.8%、大量开源服务器存在认证问题，需深度防御、标准化安全审计与社区教育[22]。
- **企业级功能落后**：审计日志、SSO 集成、细粒度访问控制仍落后于传统企业标准；与 A2A 的无缝集成及与 ACP 遗留系统兼容仍需实践与标准化；多模态支持尚待扩展[22]。
- **其他不确定性**：MCP 目前缺乏远程调用能力，需未来加入认证和联网才能适配微服务、云 API 场景；官方尚无 MCP 市场，仅有 MCP.so、Glama、PulseMCP 等社区平台；更新阶段存在权限持久化、回退到易受攻击版本、配置漂移等风险，建议建立官方包管理系统。此外 MCP 未设置工具选择规则，Agent 生态中竞争合作合理性与"自我优待"边界尚缺乏监管判断标准[37][38][39]。
