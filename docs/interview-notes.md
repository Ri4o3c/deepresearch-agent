# 面试话术笔记（DeepResearch 多 Agent 研究助手）

> 随项目推进持续更新。数字都来自本项目真实运行结果，换数据后记得更新。

## 一句话介绍
基于 LangGraph 的多 Agent 深度研究系统：规划 Agent 拆解问题 → 多个检索 Agent 并行联网检索 → 写手 Agent 生成带引用报告 → 审稿 Agent 评分并触发补查的反思循环。

## 1. 结构化输出（planner.py / researcher.py / reviewer.py）
- 用 Pydantic 定义输出 schema，`with_structured_output(method="function_calling")`，底层让模型以函数调用形式返回 JSON，比让模型在文本里写 JSON 更稳定。
- 下游 Agent 直接消费结构化数据（子问题列表、带 source_ids 的要点），Agent 之间的接口清晰。

## 2. 上下文压缩与幻觉控制（researcher.py）
- 网页正文截断到 1500 字，是最简单的上下文压缩，避免 token 暴涨。
- 每条要点强制标注 source_ids；System Prompt 要求"只使用资料中的信息"；temperature=0。
- 本质是联网 RAG：检索 → 拼接上下文 → 基于资料生成。

## 3. LangGraph 核心概念（graph.py）
- **State**：所有节点共享的状态"白板"，节点返回部分更新。
- **Reducer**：`Annotated[list, operator.add]`，并行节点写同一字段时拼接而不是覆盖。
- **Send API**：根据子问题数量动态派发 N 个检索 Agent 并行执行（Map-Reduce）。
- **stream_mode="updates"**：每个节点完成就推送事件，用于前端实时展示 Agent 进度。
- 效果：6 个检索 Agent 并行，检索阶段约 7 秒完成；串行预计 40 秒以上。

## 4. 引用全局重编号（graph.py writer_node）
- 每个检索 Agent 都有自己的 [1]…[n]，写作前按 URL 去重并统一编号，保证报告引用不冲突。属于自己实现的细节，可主动讲。

## 5. 反思循环（reviewer.py + after_review 条件边）
- 审稿 Agent 输出 score / passed / issues / follow_up_questions。
- 条件边：通过 / 无补查问题 / 达到 MAX_ROUNDS=2 → 结束；否则只对**新增补查问题**并行检索（增量补查，不从头重跑）。
- **面试必问"如何保证循环会终止"**：硬上限 MAX_ROUNDS + 通过条件 + 补查问题为空，三重终止条件。

## 6. 迭代优化故事（STAR，重点讲）
- **问题**：审稿 Agent 标准过严（要求一手官方文档），反思循环总是跑满上限；检索结果混入无关内容（例如一条马术新闻被当成 CrewAI 资料引用）。
- **方案**：
  1. 审稿引入量化评分细则：覆盖度 / 证据 / 一致性 / 结论 4 个维度各 2.5 分，>=7 分通过，issues 最多 5 条；
  2. 检索加两级来源过滤：Tavily 相关度分数 >=0.3 粗筛 + LLM 主题相关性判断精筛。
- **结果（真实数据）**：首轮评分 5/10 → 7/10 并一次通过；反思轮数 2 → 1；单份报告耗时 85 秒 → 36 秒。
- **话术**："一开始审稿 Agent 标准过严，反思循环总是跑满上限。我引入了量化评分细则和来源相关性过滤以后，首轮通过率提升，单份报告耗时从 85 秒降到 36 秒。"

## 7. 工程细节
- `llm.py` 统一封装模型创建，方便切换模型或按 Agent 分级用模型（成本优化）。
- API Key 走系统环境变量，不写入代码和仓库。

## 8. 评测体系与系统性优化（eval/run_eval.py）
- 自建评测脚本：3 类问题（技术对比 / 行业趋势 / 概念解释），记录耗时、审稿评分、反思轮数、token、引用有效性（引用编号是否都能在参考资料中找到）。
- **基线问题诊断**（从审稿意见中归纳共性）：
  1. 检索落空导致跑题（某子问题过滤后 0 条资料，写手用无关内容填充）；
  2. 多来源数据矛盾未处理；
  3. 模型缺少时间感，把近期事实误判为"未来"；
  4. bug：修订轮写手看不到审稿意见，补查后分数只涨 1 分。
- **对应优化**：资料不足时 LLM 改写查询重试，仍不足则显式标注"资料不足"；写手 Prompt 增加冲突数据处理、事实/预测区分、一致性要求；所有 Agent 注入当前日期；修订轮把审稿意见传给写手。
- **工程问题**：并发 6 路触发 DeepSeek 429 并发限制 → 图级 max_concurrency=3 + 模型调用 max_retries=6 指数退避。面试可讲"真实生产问题：限流与重试"。
- **结果（真实数据）**：
  | 版本 | 技术对比 | 行业趋势 | 概念解释 | 通过率 |
  |---|---|---|---|---|
  | 基线 | 5→6 分（2轮未通过） | 7 | 8 | 2/3 |
  | 优化后第1轮 | 7 | 7 | 8 | 3/3 |
  | 优化后第2轮 | 8 | 8 | 8 | 3/3 |
  - 引用有效率 100%（无悬空引用编号）；技术对比题 token 输入从 6.4 万降到约 4.6 万。
- **话术**："我建了一个小评测集，从审稿意见里归纳出 4 类共性问题逐一修复，通过率从 2/3 提到 3/3，平均评分从 6.7 提到 8；过程中还遇到 API 并发限流，用并发上限加指数退避解决。"

## 9. 服务化：FastAPI + SSE 流式 + 断点续跑（app/server.py）
- 接口：`POST /research/stream` 启动并以 SSE 流式推送每个 Agent 的事件（start / node / done / error）；`POST /research/{id}/resume` 断点续跑；`GET /research/{id}` 查询任务状态。
- **为什么用 SSE 不用 WebSocket**：服务端到客户端的单向推送，SSE 基于普通 HTTP，自动重连，实现和部署更简单；需要双向交互（如人工审批）时再考虑 WebSocket。
- **事件压缩**：`_summarize()` 只推送前端需要的字段（子问题、来源数、评分），不推整份笔记，降低带宽。
- **Checkpoint 断点续跑**：LangGraph 编译时挂 SqliteSaver，以 thread_id 区分任务，每个超步（super-step）后自动持久化状态。
- **真实测试**：任务跑到 2/6 个检索 Agent 时**强制杀掉服务进程**，重启后查询状态显示 notes=2、待执行 4 个 researcher；调用续跑后**已完成的 2 个直接从 checkpoint 的 pending writes 恢复（不重复调用模型）**，只执行剩余 4 个，最终 notes=6 无重复，报告正常生成、审稿 8 分通过。
- **话术**："我在服务化时用 LangGraph 的 SQLite checkpointer 实现了断点续跑，测试中在并行检索中途强杀进程，重启后能精确从中断处继续，已完成的并行分支不会重复执行，避免浪费 token。"

## 10. 服务接口测试（eval/test_server.py，19 项用例 × 3 轮）
> 适用范围：下面的轮次和通过数只属于当时那版服务测试，不是 2026-11-07 未运行的新源码结果。
- 覆盖：正常流程（事件顺序、无内部事件泄露、报告完整）、异常输入（空/纯空格/超长/缺字段）、404/400 状态码、2 任务并发、客户端中途断开后续跑、进程崩溃后续跑。
- **发现并修复的 2 个 bug**：
  1. 空问题、纯空格问题、5000 字超长问题都会被接受并直接启动研究（浪费 token，空请求还会卡住连接）→ Pydantic `Field(min_length=2, max_length=500)` + `field_validator` 去除首尾空格，统一返回 422。
  2. 审稿通过时，"补充建议问题"仍被并入 `sub_questions`，导致状态里子问题 9 个、实际笔记只有 6 个，数据不一致 → 只有真正触发补查时才并入，并对补查问题去重。
- **结果**：第 1 轮 18/19 → 第 2、3 轮均 19/19 通过；崩溃续跑后笔记数与子问题数严格一一对应、无重复。
- **话术**："我给服务写了 19 个接口用例，包括强杀进程后续跑、并发和客户端断开，测出了输入校验缺失和状态不一致两个 bug，修复后连续两轮全部通过。"

## 11. 前端：Vue3 + TypeScript 实时可视化（web/）
> 适用范围：本节的粒子背景、打字机和 npm/e2e 轮次属于当时的界面与测试。不代表 2026-11-07 已改但未运行的工作台。11 月 6 日 99 项离线窄链路不覆盖这版新界面。
- **技术栈**：Vite 8 + Vue 3.5 + TypeScript，运行时依赖只有 `vue` 和 `markdown-it` 两个；生产包 JS 193.9 KB（gzip 79.7 KB）、CSS 13.7 KB（gzip 3.9 KB），构建约 0.2 s，开发服务器冷启动约 0.3 s。
- **为什么用 fetch + ReadableStream 解析 SSE，不用 EventSource**：EventSource 只支持 GET、不能带 JSON 请求体；我用 fetch 发 POST，自己按 SSE 规范解析（`\r\n` 归一化、空行分帧、忽略 `:` 心跳注释、多行 data 拼接），还能用 AbortController 随时停止。
- **状态机**：`store.ts` 把 start / node / done / error 事件映射成界面状态：planner 完成后按子问题数动态生成 N 张检索卡片（并行出现），全部检索完成后 Writer 亮起，审稿打回时轮次 +1，并按补查问题新增卡片，展示反思回路。researcher 事件按问题文本匹配卡片，匹配不上（问题被改写）时回退到当前轮第一张运行中的卡片。
- **断点续跑的前端设计**：先 `GET /research/{id}` 拿快照恢复界面（已完成的卡片、审稿记录、轮次），再根据快照里的 `next` 点亮即将执行的节点，然后调 resume 继续接收流；thread_id 历史存在 localStorage，刷新页面后也能找回任务。
- **交互效果**：Canvas 粒子"知识图谱"背景（节点靠近自动连线、鼠标吸引并高亮、连线上流动信息脉冲，研究进行中会加速变亮）+ 极光渐变 + 网格；毛玻璃面板、鼠标跟随高光；节点运行时呼吸发光、边上有流光动画；报告打字机式逐段出现（约 1.5 s，可跳过）；正文 `[n]` 自动变成可点击的引用角标，悬停显示来源标题；支持复制和下载 Markdown；支持 `prefers-reduced-motion`。
- **错误体验**：422 映射成中文提示（"问题太短/太长"）；后端没启动时代理返回 502，提示"请先运行 uvicorn"；流意外中断时显示"从断点续跑"按钮；后端在线状态每 10 s 检测一次。
- **测试（3 轮）**：`npm test` 用录制的事件序列回放 store（12 项断言，含反思回路与续跑）；`npm run e2e` 经 Vite 代理调真实后端（17 项断言：事件字段、422×3、404、400、快照一致、引用可解析）；`npm run test:resume` 在 planner 后主动断开连接，再续跑（5 项断言）。
  | 轮次 | 构建 | store 回放 | e2e 完整研究 | 断开后续跑 |
  |---|---|---|---|---|
  | 第 1 轮 | 通过 | 9/9 | 17/17，45.8 s，审稿 7 分，26 条引用 | 5/5，35.8 s（未重跑 planner） |
  | 第 2 轮 | 通过 | 12/12 | 17/17，47.7 s，8 分 | 5/5，32.9 s |
  | 第 3 轮 | 通过 | 12/12 | 17/17，60.5 s，7 分，34 条引用 | 5/5，37.3 s |
  - 用 4 份真实报告校验引用：正文引用编号全部能在参考资料中找到（0 悬空），单份报告生成 81~151 个可点击角标。
- **修掉的问题**：① 引用正则把"参考资料"行首的 [n] 也替换成链接 → 改成按行识别参考资料行并跳过；② 续跑恢复界面时卡片不亮、轮次算错，GET 失败后仍会去调 resume → 按快照的 next 点亮节点，轮次 = 审稿次数 + 1，GET 失败则中止；③ 后端没启动时只显示"HTTP 502"，健康状态只在页面加载时检测一次 → 提示具体操作，并改为定时检测；④ 缺字段的 422 返回英文提示 → 映射成中文。
- **话术**："前端我没有用 EventSource，因为它不支持 POST，所以自己用 fetch 和 ReadableStream 实现了 SSE 解析，把后端的节点事件映射成状态机，实时画出 Planner、N 个并行 Researcher、Writer、Reviewer 的执行过程和反思回路。断点续跑时先拉快照恢复界面再接流。测试上，我把真实的事件序列录下来回放给状态机做单测，再经代理跑端到端测试，连续三轮全部通过，打包后 gzip 只有 80 KB 左右。"


## 12. RAG 本地知识库（app/rag/，混合检索 + 重排）

**做了什么**：用户上传 PDF/Markdown/TXT → 解析分页 → 递归切块（500 字、80 重叠，保留页码）→ DashScope `text-embedding-v3` 向量化存 Chroma（`data/chroma`，cosine）+ jieba 分词建 BM25 → 检索时向量、BM25 各召回 20 条，RRF(k=60) 融合，再用 `gte-rerank-v2` 重排取 top-k。封装成 `kb_search` 工具接入 Researcher：每个子问题同时查网页(8)和本地库，统一编号，来源打 `type: web/local` 标签，Prompt 规定本地文档优先；报告里本地引用带"📄本地："前缀和 `/api/kb/docs/{id}/file#page=p` 原文链接，前端显示绿色 📄 徽章、可点开原文。接口：`POST /kb/upload`（多文件、20MB 限制、扩展名/空文件校验）、`GET /kb/docs`、`DELETE /kb/docs/{id}`、`GET /kb/docs/{id}/file`、`GET /kb/search`（调试）。前端加了知识库面板：拖拽上传、进度条、索引中状态、文档列表、删除。

**为什么这样选**
- 混合检索：向量擅长语义改写，BM25 擅长专有名词/数字（"8812"、"120 秒"），两者互补；RRF 只看排名不看分数，免去两路分数归一化。
- 中文 BM25 必须先分词：jieba `cut_for_search` + 停用词，否则按字切召回很差。
- 重排：召回求全、重排求准；重排失败自动降级为 RRF 顺序，不影响主流程。
- 用云端 embedding/rerank 而不是本地 bge：Windows 笔记本无 GPU，本地模型拖慢启动，也会让依赖变重。
- Ragas 单独放 `.venv-eval`：ragas 0.4.3 会把主环境 langchain-openai 从 1.7.3 降到 1.1.9，评测依赖不能污染业务环境。

**检索评测**（eval/rag：3 篇 arXiv 论文 RAG/ReAct/Lost in the Middle + 2 篇中文笔记 + 1 篇虚构运维手册，15 道题；命中 = 来自标准答案文件且含关键词）

| 模式 | Hit@1 | Hit@3 | Hit@5 | MRR | 延迟 |
|---|---|---|---|---|---|
| 纯向量 | 0.867 | 0.867 | 0.867 | 0.867 | 1469ms |
| 纯 BM25 | 0.733 | 0.733 | 0.800 | 0.747 | 78ms |
| 混合(RRF) | 0.733 | 0.933 | **1.000** | 0.824 | 1404ms |
| 混合+重排 | **0.933** | 0.933 | 0.933 | **0.933** | 4515ms |

结论：混合检索把 Hit@5 拉到 1.0（召回最好），重排把 Hit@1 从 0.733 提到 0.933、MRR 从 0.824 提到 0.933（排序最好），代价是多 3 秒。唯一的失败是"RAG 的 retriever/generator 分别是什么"：混合检索排第 3，重排后被挤出前 5，说明重排模型对英文论文长段落不够稳。

**Ragas 生成评测**（混合+重排 top4，DeepSeek 作答和打分）：faithfulness **1.0**、answer_relevancy **0.835**、context_precision **0.922**。answer_relevancy 偏低的是简短答案（如 recursion_limit 0.44），这是指标对短答案偏严，不是答错。

**入库性能**：embedding 原来串行一批 10 条，RAG 论文 186 块要 40s；改成 4 线程并行后 13.5s，约快 3 倍。

**测试（3 轮）**（历史轮次，只说明当时的 RAG/前端测试；不覆盖 2026-11-07 未运行的新界面）
- 第 1 轮：`eval/test_rag.py` 18/18（切块/分词/RRF 单元、临时库存储、TestClient API、Researcher 本地来源集成），前端 refs 9/9、store 测试通过、build 通过；端到端（经 Vite 代理上传→流式研究→检查报告→清理）失败：①上传 502；②报告里本地原文链接打不开。
- 第 2 轮：修复后 test_rag 18/18、npm test（store + refs）通过、build 通过、端到端 **通过**（6 个 Researcher 都用上本地来源，报告含"120 秒""8812"，本地链接 2/2 可打开，清理后知识库为空）。
- 第 3 轮：新增链接修复用例，test_rag 19/19，端到端再次通过，前端测试与构建通过。原有 test_server 跑到一半 DeepSeek 返回 402 余额不足，该轮未得出有效结论（详见缺口）。

**踩过的坑**
1. Chroma 集合名 "kb" 不合法（至少 3 个字符）→ 改为 `knowledge_base`，并设 `embedding_function=None` 避免它去下载默认模型。
2. 端到端上传 502：Windows 设了系统代理 127.0.0.1:1088，httpx 默认 `trust_env` 读到后把 localhost 请求也走代理；curl 不受影响所以一开始很迷惑。测试客户端加 `trust_env=False`。（同样的坑也会影响任何用 httpx 调本机服务的脚本。）
3. **LLM 抄错 ID**：写手照抄参考资料时，把 10 位文档 ID 改错了一两个字符，链接 404。不能指望 Prompt 解决 → 在 writer 后加确定性校验 `fix_local_links`：ID 不在本次来源中时，按同一行的文件名 + 页码换回真实链接。经验：**凡是 LLM 需要逐字复制的标识符，都要在代码里做后校验**。
4. Ragas 依赖冲突（见上）；ragas 0.4.3 还要求 `langchain_community.chat_models.vertexai`，所以评测环境固定 langchain* 0.3 系列。
5. test_server 自己会起 8000 端口，必须先停开发服务器，否则测到的是旧进程。

**缺口 / 下一步**
- 重排在英文长段落上偶尔把正确结果挤掉 → 可试"重排分数 + RRF 名次"加权，或只在 top-10 内重排。
- 评测集只有 15 题，结果有波动（两次建库向量 MRR 0.867/0.88），应扩到 100+ 题。
- 暂不支持 docx/扫描版 PDF（无 OCR）；BM25 全量内存重建，文档多了要换增量索引。

## 13. 可观测性：自部署 Langfuse（app/observability.py，docker/langfuse/）
- **为什么选 Langfuse 不选 LangSmith**：开源可自部署，数据留在本机、国内网络无障碍；不绑定 LangChain。用官方 docker compose 拉起 web/worker + Postgres（元数据）+ ClickHouse（trace 分析）+ Redis（队列）+ MinIO（事件/媒体存储），本机实测 Langfuse 4.75.0 约 2 分钟就绪。
- **接入方式**：LangGraph 通过 runnable config 注入 Langfuse 的 LangChain CallbackHandler，所有节点和 LLM 调用自动成树；`langfuse_session_id = thread_id`，断点续跑和首次运行归到同一 Session；用 tags 区分 start/resume/cli。Tavily 和本地知识库不是 LangChain 组件，用 `start_as_current_observation` 手动包成 tool / retriever span。
- **工程取舍**：可观测性是"旁路"，不能影响主流程——未配置密钥时完全 no-op；配置了但服务不可达时只打 warning（单测用假密钥 + 不可达端口验证，4 项用例 11s 内通过，不发起外网请求）；FastAPI lifespan 关闭时 flush，避免丢最后一批 trace。
- **安全**：compose 中所有端口只绑定 127.0.0.1，密钥放在被 gitignore 的 .env，只提交 .env.example。
- **测试**（按省 token 要求 1 轮）：tests/test_observability 4/4，eval.test_rag 20/20，服务模块导入与 lifespan 检查通过。- **真实运行验证**（问题"什么是 RRF 倒数排名融合？"，Tavily 当时已超额，自动降级为只用本地库）：1 条 trace、session_id 正确，共 123 个 observation（CHAIN 56 / GENERATION 19 / TOOL 36 / RETRIEVER 12）；planner 1、researcher 12、writer 3、reviewer 3（触发了 2 轮反思补查），tavily_search 36、kb_search 12；端到端 41.9s，19 次 LLM 调用共 18947 tokens（含缓存命中统计）。Langfuse 内置价格表没有 deepseek-chat，所以成本显示为 0，需要在 Models 里手动配置单价。
- **踩坑**：自部署的 Langfuse v4 是 events_only 模式，旧的 `/api/public/traces` 查询接口返回 404，要用 `/api/public/v2/observations` 按 traceId 聚合；SDK 5.x 走 OpenTelemetry 上报。
## 14. 网页搜索可插拔：自部署 SearXNG 替代 Tavily（app/search/）
- **背景**：Tavily 免费额度耗尽，整条研究只能退化为本地库。抽象出 `SearchProvider` 接口（searxng 主 / ddgs 备 / tavily 可选），`SEARCH_PROVIDERS` 控制顺序，报错或空结果自动降级；全部失败再交给 researcher 原有的"只用本地库"兜底，形成三层降级。
